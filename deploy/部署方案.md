## 1. 方案总览

### 1.1 这套东西在干嘛

用大白话说，三个概念：

| 名词 | 是什么 |
|---|---|
| **Ansible** | 服务器**配置管理**工具。你写一份「服务器应该长什么样」的说明书（playbook），它去把服务器改成那样。重复执行结果一样（幂等） |
| **GitHub Actions** | GitHub 免费借你一台临时电脑。你 `git push` 之后它自动编译代码、把成品送到服务器。跑完就销毁 |
| **Secrets** | 存密码的地方。服务器 IP、SSH 私钥、数据库密码不写在代码里，存在 GitHub 仓库设置或 Ansible Vault 里 |

**完整流程**：

```
① 你（本地）   ansible-playbook site.yml   →  把服务器配好：Docker、目录、数据库、.env
② 你（本地）   git push main
③ GitHub       临时电脑编译 jar + dist
④ GitHub       SSH 直传服务器 → Docker 重建 → 冒烟测试
⑤ 你（外网）   打开 http://<IP>:8081 验收
```

**①只做一次**（或者改配置时做），**②~⑤每次发版都做**。

### 1.2 为什么不走镜像仓库

业界标准做法是把编译好的镜像推到镜像仓库（如 ghcr.io），服务器自己去拉。但你的服务器在**阿里云（国内）**，拉 `ghcr.io` 经常超时失败。

这个项目就一个 jar 加一堆静态文件，**直接用 SSH 传更省事**。代价是服务器第一次要联网拉两个基础镜像（`eclipse-temurin:21-jre`、`nginx:alpine`），这两个**只拉一次，之后永久缓存**——所以只有首次部署会碰网络问题。

### 1.3 最终架构

```
┌─────────── 你的 Windows ───────────┐
│  WSL2 + Ansible  ──┐               │
│  浏览器            │               │
└────────────────────┼───────────────┘
                     │ ① ansible-playbook（SSH）
                     │ ② git push
                     ▼
        ┌──── GitHub Actions ────┐
        │  build-backend  jar    │
        │  build-frontend dist   │
        │  deploy  → scp + ssh   │
        └────────────┬───────────┘
                     │ ③ SSH 直传
                     ▼
┌─────────────────── 阿里云 ECS ───────────────────┐
│  公网 :8081                                       │
│   └─ myblog-nginx ──┬── /       → 博客前端静态文件 │
│                     └── /api/   → myblog-backend  │
│   └─ myblog-backend（java -jar app.jar）          │
│         │                                         │
│         ├── myblog-redis   （博客自己的 Redis）   │
│         └── myapp-mysql    （★另一个项目的容器，  │
│                              博客只新建 myblog 库，│
│                              碰不到它的 tlias 库）│
└───────────────────────────────────────────────────┘
```

### 1.4 与现有 `myapp-*` 项目的隔离边界

服务器上已经跑着**另一个项目**（`myapp-frontend` / `myapp-backend` / `myapp-mysql`），本方案**不改动它的任何东西**。

| 维度 | 博客 | 另一个项目 | 是否冲突 |
|---|---|---|---|
| 容器名 | `myblog-*` | `myapp-*` | 否 |
| Docker 网络 | `myblog_net` | `myapp_app-network` | 否 |
| 公网端口 | **8081** | 80、8080 | 否 |
| 数据卷 | `/opt/myblog/*` | `/opt/myapp/*` | 否 |
| 数据库 | `myblog` 库（专用账号，只能访问本库） | `tlias` 库 | 否 |

**唯一的接触点**：博客的 backend 容器会**额外接入** `myapp_app-network` 这一个网络，目的是能按名字访问到 `myapp-mysql`。除此之外两边互不可见——另一个项目的容器访问不到博客的 Redis 和 Nginx。

> ⚠️ 由此带来一条纪律：**不要删除 `myapp_app-network` 网络，也不要在 `/opt/myblog` 里执行 `docker compose down -v`**。删了网络博客就连不上数据库了。
>
> ✅ 好消息：**Ansible 全程不需要知道 `myapp-mysql` 的 root 密码**。因为建库命令是丢进容器里执行的，root 密码用它自己容器内的环境变量，不经过我们。这也意味着你的 Vault 里不用存别人的密码。

### 1.5 为什么 Nginx 必须参与

前端 `myblog-frontend/src/api/request.js` 里的 `baseURL` 是**相对路径 `/api`**。开发时靠 Vite 的 proxy 转发到 8080，生产环境没有 Vite 了，必须由 Nginx 做同源反向代理。

顺带这也免掉了后端 CORS——项目里本来就没有 CORS 配置类，这与 `个人博客开发方案.md` 第 1040 行的约定「生产期用 Nginx 反向代理」一致。

### 1.6 ★ Ansible 与 GitHub Actions 的分工

这是本方案的核心设计，**两者的边界必须清晰，否则会互相打架**：

| | Ansible | GitHub Actions |
|---|---|---|
| **管什么** | 服务器**环境状态** | 每次发布的**制品** |
| **管什么** | Docker 配置、目录结构、数据库、**`.env`** | `app.jar`、`dist/`、`docker-compose.yml`、`nginx/default.conf`、`rollback.sh` |
| **频率** | 一次性 / 改环境配置时 | 每次 push |
| **怎么跑** | 本地 WSL2 里手动执行 | push 自动触发 |

**为什么 `.env` 归 Ansible，而 `docker-compose.yml` 归 CI/CD？**

- `.env` 里全是**密钥**。放进 Git 必须加密 → 这正是 **Ansible Vault** 要解决的问题。而且密钥是**环境状态**，跟代码版本无关。
- `docker-compose.yml`、`nginx/default.conf` 是**跟着代码版本走的**——你改了 nginx 配置，就应该和这次代码改动一起发出去。放 CI/CD 里最顺。

**记住这条分界线**：改 `.env` 或系统配置 → 重跑 Ansible；改代码或 nginx/compose 配置 → push。

### 1.7 为什么日志和监控不在这台服务器上做

**内存不够，就是这么简单。**

这台机器 1.7 GiB 内存，已用 952 MiB，只剩 638 MiB 可用。算一笔账：

| 层 | 内存 |
|---|---|
| 系统 + 另一个项目 + 你的博客 | ~1292 MiB |
| 日志套件（Loki + Promtail + Grafana） | ~250 MiB |
| 监控套件（Prometheus + node_exporter + cAdvisor） | ~225 MiB |
| **合计** | **~1767 MiB** ← 超过物理内存 |

而 **Zabbix Server 单独就要 500 MiB+，还得配一个数据库**，根本装不下。

所以：**生产服务器只做 CI/CD + Ansible（零额外内存），日志监控这些学习性质的内容放到本地虚拟机做全套**——那里内存管够，而且可以随便折腾、随便搞挂。

→ 详见配套文档 `运维练习方案.md`

## 3. 阶段一：准备（本地 + 服务器前置）

> **A~E 在 WSL 里操作**，不在 Windows 上做任何事。**F 是服务器上的操作**，必须在跑 Ansible 之前完成。
>
> 为什么：密钥的唯一使用者是 **Ansible** 和 **GitHub Actions**，而 Ansible 只能跑在 Linux 上。**让密钥从一开始就生成在它要被用的地方**，比生成在 Windows 再拷过去简单得多——省掉一次复制，也省掉后面那个权限坑。

### A. 安装 WSL2 + Ansible

**⚠️ 先说一个坑：Ansible 的控制端不能跑在 Windows 上**，官方只支持 Linux/macOS 作为控制节点。Windows 11 上用 WSL2 是最省事的路子。

在 **PowerShell** 里执行：

```powershell
wsl --install -d Ubuntu
```

装完重启，设好 Ubuntu 用户名密码，然后**在 Ubuntu 终端里**执行：

```bash
sudo apt update && sudo apt install -y ansible
ansible --version
```

**⚠️ 检查 Ansible 版本**：

```bash
ansible --version
```

记下版本号（2.17 / 2.18 / 2.19 都行，**不用管**）。apt 装的通常是最新版，这没问题——**我们在服务器侧解决 Python 版本问题**（见后面的 **F 节**），不在本地降级 Ansible。

> 如果你显示 2.17 或更高，跑第一次 `ping` 时会看到 `SyntaxError: future feature annotations is not defined`。原因是 CentOS 8 自带的 `/usr/libexec/platform-python` 是 **3.6.8**，而 ansible-core 2.17 起要求目标机 Python ≥ 3.7。
>
> **两条路，本方案走第二条**：
> - 方案 A：本地把 Ansible 降到 2.16.x（`pip install "ansible-core<2.17"`）。缺点是本地被钉死在旧版本，而且 apt 装的 Ansible 在 PEP 668 保护的目录里，`pip install` 会被 `externally-managed-environment` 挡住，还得额外开 venv 或加 `--break-system-packages`，很绕。
> - **方案 B（推荐）：服务器上装 Python 3.9**，让 Ansible 用它干活。本地 Ansible 保持最新，服务器也拿到了新版 Python。见 **F 节**。

### B. 在 WSL 里生成密钥

```bash
ssh-keygen -t ed25519 -C "myblog-deploy" -f ~/.ssh/myblog_deploy
```

一路回车（**不要设密码短语**，否则 Ansible 和 CI 都用不了）。

> **`-t ed25519` 和 `-t rsa` 怎么选**：ed25519 更短、更快、更安全，现代系统都支持。只在需要兼容很老的设备时才用 rsa。
>
> **这一步不能懒省事不加 `-f`**：不加的话会生成到默认路径 `~/.ssh/id_ed25519`，和你的个人密钥混在一起。**给每套用途单独一把密钥**是好习惯——万一泄露了，只吊销这一把。

生成两个文件：

| 文件 | 用途 |
|---|---|
| `~/.ssh/myblog_deploy` | **私钥** → Ansible 用它，GitHub Secrets 也用它的内容 |
| `~/.ssh/myblog_deploy.pub` | **公钥** → 装到服务器上 |

### C. 把公钥装到服务器

**WSL 里有 `ssh-copy-id`，一条命令搞定**（这是坚持在 WSL 里做的主要好处之一，Windows PowerShell 里没有这个命令）：

```bash
ssh-copy-id -i ~/.ssh/myblog_deploy.pub root@<你的服务器IP>
```

会提示输入一次服务器的 root 密码，然后它自动完成三件事：建 `~/.ssh` 目录、设好权限、把公钥追加进 `authorized_keys`。

> **`-i` 后面跟的是 `.pub` 公钥文件**，不是私钥。这是个高频手误点。

**验证免密登录**：

```bash
ssh -i ~/.ssh/myblog_deploy root@<你的服务器IP> "docker --version"
```

能直接打印出 Docker 版本、**没让你输密码**，就说明成功了。

**如果服务器禁用了密码登录**，`ssh-copy-id` 会因为没密码可输而失败。这时候你本来就是用**某把已有密钥**登进去的，那就借它把新公钥捎进去：

```bash
cat ~/.ssh/myblog_deploy.pub | ssh -i ~/.ssh/你现有的密钥 root@<你的服务器IP> \
  "mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys"
```

> 阿里云 ECS 默认**允许** root 密码登录，所以正常情况下 `ssh-copy-id` 直接就能用，不用管这段。

### D. 配置 `~/.ssh/config`（强烈建议）

每次都敲 `-i ~/.ssh/myblog_deploy root@<IP>` 太啰嗦。写个别名：

```bash
cat >> ~/.ssh/config <<'EOF'

Host myblog
    HostName <你的服务器IP>
    User root
    IdentityFile ~/.ssh/myblog_deploy
    ServerAliveInterval 60
EOF

chmod 600 ~/.ssh/config
```

之后 `ssh myblog` 就能直接进服务器，`scp`、`rsync` 也都能用 `myblog:` 这个简写。

> `ServerAliveInterval 60` 是防止网络波动时 SSH 莫名其妙断线——国内连云服务器很常见。

### E. 顺便学一手：批量分发公钥

你手上的教程讲的是**用 `expect` 自动输密码、循环给一批机器发公钥**——那是**运维管一批服务器**的常规做法。

**你的场景不一样**：只有**一台**服务器，`ssh-copy-id` 一条命令就够了，用不着 `expect`。

但既然你在学运维，这里把两种做法都过一遍。**注意它们的适用场景差异**：

**做法一：`expect` + 循环（Shell 派）**

适用于**手头没有 Ansible、机器是一批、且只能用密码登录**的场景：

```bash
# 先装 expect
sudo apt install -y expect        # Ubuntu/Debian
# yum install -y expect           # CentOS/RHEL

# host.txt：IP 用户 密码（空格分隔，不要有空行和注释）
cat > ~/host.txt <<'EOF'
10.0.0.11 root 123456
10.0.0.12 root 123456
10.0.0.13 root 123456
EOF

# 循环分发
while read ip username password; do
expect <<EOF
    spawn ssh-copy-id $username@$ip
    expect {
        "yes/no"   { send "yes\r"; exp_continue }
        "password" { send "$password\r" }
    }
    expect eof
EOF
done < ~/host.txt
```

**做法二：Ansible 的 `authorized_key` 模块（★ 你该用的）**

既然你在学 Ansible，同一件事它有**原生、幂等**的做法：

```yaml
# bootstrap-keys.yml
---
- name: 首次分发公钥
  hosts: all
  gather_facts: false
  tasks:
    - name: 安装公钥
      ansible.posix.authorized_key:
        user: root
        state: present
        key: "{{ lookup('file', '~/.ssh/myblog_deploy.pub') }}"
```

首次运行需要密码（因为还没免密），用 `--ask-pass` 输一次：

```bash
ansible-galaxy collection install ansible.posix
ansible-playbook bootstrap-keys.yml -i inventory.ini --ask-pass
```

**两种做法的区别**（★ 这就是 Ansible 的价值）：

| | `expect` 脚本 | Ansible `authorized_key` |
|---|---|---|
| 重跑一次 | 再追加一遍（**`authorized_keys` 里出现重复行**） | 检查后跳过，`changed=0` |
| 密码怎么给 | 明文写在 `host.txt` 里躺着 | `--ask-pass` 交互输入，不落盘 |
| 出错怎么办 | 循环继续跑，你不知道哪台失败了 | 哪台失败报哪台，`--limit` 单独重试 |
| 换一批机器 | 改 `host.txt` | 改 inventory |

**记住这个对比。** 以后遇到「用 shell 脚本循环 SSH 一堆机器」的场景，先想想 **Ansible 有没有现成的模块**——绝大多数情况都有，而且幂等、有日志、能单独重试。

**你的博客部署用不上这段**（只有一台服务器），但**在虚拟机上练多机管理时（见 `运维练习方案.md` 模块 0）正好用得上**。

### F. ★ 服务器前置：修复 CentOS 8 源 + 装 Python 3.9

> **这一步在服务器上做，不是本地。** 它是**跑 Ansible 之前的最后一道坎**。

#### 为什么必须做：Ansible 的「先有鸡还是先有蛋」

Ansible 管理一台机器的方式是：**把一小段 Python 脚本传过去，用目标机上的 Python 执行**。

而你的服务器是 CentOS 8，系统 Python 停在 **3.6.8**（2021 年的东西）。新版 Ansible 生成的脚本用了 Python 3.7+ 的语法，结果就是：

```
File ".../AnsiballZ_ping.py", line 3
    from __future__ import annotations
    ^
SyntaxError: future feature annotations is not defined
```

**这就是个死循环**：想用 Ansible 装 Python，可 Ansible 自己就需要一个新 Python。

**打破循环的办法只有一个：先手工把 Python 装好。**

#### 为什么不降级 Ansible 而要动服务器

降级本地的 Ansible（`pip install "ansible-core<2.17"`）**也**能解决，而且只动本地、更安全。但这里选修服务器，理由是：

- **CentOS 8 在 2021 年底就 EOL 了，yum 源是死的**。不修的话，你以后在服务器上**装任何东西都会失败**——这是个迟早要还的债，现在就还掉。
- 修完之后 Ansible 可以用最新版，你学的不是个被钉死在 2.16 的老工具。

> **代价**：要改生产服务器的 yum 配置。**但只改"从哪里下载包"，不碰任何运行中的东西**，包括另一个项目的容器。

#### ⚠️ 先划清范围

| 做 | **不做** |
|---|---|
| 改 yum 源 → 阿里云归档站 | ❌ **`dnf update` / `dnf upgrade`** |
| `dnf install python39` | ❌ 升级内核 / glibc / systemd |
| | ❌ 改系统默认 `python3`（还是 3.6） |

**绝对不要顺手 `dnf update`。**

这台机器已经落后 5 年更新，一次性 `dnf update` 会拉进来 glibc、内核、systemd 的跨大版本变化——**在跑着别人项目的生产机上，这是典型的「本来没事，一升级全挂」**，而且很可能要求重启。

**我们只要「装一个 Python 3.9」，不是「把系统翻新」。**

#### F-1. 备份

```bash
# 在服务器上执行
cp -a /etc/yum.repos.d /root/yum.repos.d.bak.$(date +%F)
ls -d /root/yum.repos.d.bak.*
```

改坏了能一条命令回滚（**先记下来，别执行**）：

```bash
rm -rf /etc/yum.repos.d && mv /root/yum.repos.d.bak.<日期> /etc/yum.repos.d && dnf clean all
```

#### F-2. 确认系统版本

```bash
cat /etc/redhat-release
```

**输出决定下一步填哪个版本号**：

| 输出 | 填什么 |
|---|---|
| `CentOS Linux release 8.5.2111` | `8.5.2111` |
| `CentOS Stream release 8` | `8-stream` |

#### F-3. 把源指向阿里云归档站

> **为什么用阿里云而不是官方的 `vault.centos.org`**：你的 ECS 就在阿里云机房里，**走内网镜像站，速度和稳定性完全不是一个级别**。官方 vault 站从国内访问经常慢到 `dnf makecache` 卡死超时。

```bash
# ★ 按上一步的结果选一个
VAULT_VER=8.5.2111
# VAULT_VER=8-stream

echo "使用版本：$VAULT_VER"

sed -i -e 's|^mirrorlist=|#mirrorlist=|g' \
       -e "s|^#baseurl=http://mirror.centos.org/\$contentdir/\$releasever|baseurl=https://mirrors.aliyun.com/centos-vault/$VAULT_VER|g" \
       /etc/yum.repos.d/CentOS-Linux-*.repo
```

**★ 先检查改成了什么，别急着往下**：

```bash
grep -E '^#?mirrorlist|^#?baseurl' /etc/yum.repos.d/CentOS-Linux-BaseOS.repo
```

**期望输出**：

```
#mirrorlist=http://mirrorlist.centos.org/?release=$releasever&arch=$basearch&repo=BaseOS&infra=$infra
baseurl=https://mirrors.aliyun.com/centos-vault/8.5.2111/BaseOS/$basearch/os/
```

关键看两点：**`mirrorlist` 那行被注释掉了**，**`baseurl` 那行解开了并指向阿里云、版本号已替换成实际数字**。

> **如果 `baseurl` 还是 `#baseurl=...mirror.centos.org...`**，说明你的 repo 文件格式和预期不一样（不同 CentOS 8 小版本的写法有细微差别）。**停下来看 `cat /etc/yum.repos.d/CentOS-Linux-BaseOS.repo` 的实际内容再调整，别硬试。**

#### F-4. 刷新缓存

```bash
dnf clean all
dnf makecache
dnf repolist
```

**这一步就是验证源改对没有**。看到 `Metadata cache created` 就对了。卡住或报 404，停下来看报错。

#### F-5. 装 Python 3.9

```bash
dnf install -y python39
/usr/bin/python3.9 -V
```

期望输出 `Python 3.9.x`。

> **`python39` 和系统的 3.6 是并存关系**，装它**不会**改变默认的 `python3`。这正是我们要的——**最小影响面**，只有 Ansible 用它。

#### F-6. 验证 Ansible 能通了

回到 WSL：

```bash
cd ~/ansible
ansible myblog -m ping -i inventory.ini
```

**看到 `"ping": "pong"` 就成了。** ✅

## 4. 阶段二：Ansible 初始化服务器

> 这一阶段把原来「手工 SSH 上去敲一堆命令」变成**一份可重复执行的 playbook**。
> 所有文件建在 **`~/ansible/`——WSL 家目录下，不在仓库里**。

### 4.1 目录结构与位置

**⚠️ 为什么放 `~/ansible` 而不是仓库里？**

你的仓库在 `/mnt/c`（Windows 盘）下。WSL 挂载 Windows 盘时**权限一律是 `777`**，由此引发的坑会一个接一个：

- Ansible 拒绝加载「世界可写目录」里的配置（4.2 详述）
- `chmod` 基本是空操作，需要严格权限的文件（私钥、vault 文件）会出问题
- 跨 Windows/Linux 边界的 I/O 慢很多

**把文件放到 Linux 原生文件系统里，这一整类问题一次性消失。** 这是 WSL 的通用建议：**别跨 Windows/Linux 边界工作**。

```
~/ansible/                         ← WSL 家目录（★ 运行目录）
├── inventory.ini
├── site.yml
├── group_vars/
│   └── all/                       # ★ 必须是「目录」形式，见下方说明
│       ├── main.yml               # 公开变量
│       └── vault.yml              # ★ 加密的密钥（ansible-vault 生成）
└── roles/
    ├── docker/
    │   ├── tasks/main.yml
    │   ├── handlers/main.yml
    │   └── templates/daemon.json.j2
    └── myblog-init/
        ├── tasks/main.yml
        └── templates/env.j2

~/.ansible.cfg                     ← WSL 家目录
```

> **★★ 为什么 `group_vars` 必须是「目录」形式，不能写成 `all.yml` + `all.vault.yml`**
>
> 这是最容易踩、又最难自己看出来的一处。**Ansible 找 `group_vars` 的规则是「文件名 = 组名」**：
>
> | 文件 | Ansible 认为的组名 | 结果 |
> |---|---|---|
> | `group_vars/all.yml` | `all` | ✅ 加载 |
> | `group_vars/all/main.yml` | （目录形式，`all` 组下的所有文件） | ✅ 加载 |
> | `group_vars/all.vault.yml` | **`all.vault`** | ❌ **没有这个组，静默跳过** |
>
> 看出来了吗——`all.vault.yml` 去掉扩展名后，**Ansible 认为组名是 `all.vault`**，而你的清单里根本没有这个组。**它不会报错，只是安静地不加载**，然后在用到变量的地方炸出 `'vault_mysql_password' is undefined`。
>
> **报错信息离病因隔了十万八千里**：错误出现在「建库 + 建博客专用账号」这个任务里，但真正的问题在文件名。这也是本方案第一次真正跑起来时撞上的坑。
>
> **解法**：改用目录形式，让公开变量和密钥都待在 `group_vars/all/` 这个目录里，文件名随便叫（只要扩展名是 `.yml`/`.yaml`/`.json`）。

一次性创建：

```bash
cd ~
mkdir -p ansible/group_vars/all ansible/roles/docker/{tasks,handlers,templates} ansible/roles/myblog-init/{tasks,templates}
ls -R ~/ansible
```

> **★ 一个必须记住的连带后果**：playbook 不再住在仓库里，所以**它找不到仓库里的 `sql/init.sql` 了**。
> 解决办法见 **4.4 的 `project_root`**——那里必须写**绝对路径**，不能再靠 `playbook_dir` 往上退。

#### 版本控制：`~/ansible` 是运行目录，仓库那份是快照

想让这些文件进 Git（vault 的历史、回滚能力都在里面），就在改动稳定后把 `~/ansible` 拷一份回仓库：

```bash
cp -r ~/ansible/. /mnt/c/Users/huhaohua/Desktop/myproject/myblog-ai/deploy/ansible/
```

**方向只有一个：`~/ansible` → 仓库。** `~/ansible` 是唯一能正常跑的地方，**以它为准**；仓库那份是快照，不要拿来跑。（两份都能跑 = 迟早漂移）

**⚠️ 拷贝前必须确认 `group_vars/all/vault.yml` 是加密状态。**

```bash
head -1 ~/ansible/group_vars/all/vault.yml
```

**必须**输出 `$ANSIBLE_VAULT;1.1;AES256`。如果看到的是明文 YAML，**停下来先加密**——一次疏忽就是所有密钥进 Git 历史。

> **如果你用 `ansible-vault decrypt` 改过内容，改完必须 `ansible-vault encrypt` 回去。**
> 更稳的做法是用 `ansible-vault edit`，它会自动「解密 → 打开编辑器 → 存回时自动加密」，不会留下明文窗口。

`~/.ansible.cfg` 在家目录、不在 `~/ansible` 里，所以上面那条 `cp` **不会**把它带进仓库——这是对的，它属于「本机配置」，不该进仓库。

> **💡 避免两份漂移的窍门**：用 VS Code 的 **WSL 远程模式**直接打开 `~/ansible` 编辑（左下角绿色图标 → `WSL: Open Folder`）。这样既有图形编辑器，文件又始终只有一份，`cp` 就只用来提交、不再用来同步。

### 4.2 文件 1：`~/.ansible.cfg`（★ 放在 WSL 家目录）

> **为什么放家目录而不是 `~/ansible/`？**
>
> Ansible 启动时会从**当前目录**开始往上找 `ansible.cfg`。放 `~/ansible/ansible.cfg` 是完全可以的，而且更符合「配置跟着项目走」的习惯。
>
> 这里选 `~/.ansible.cfg` 只有一个理由：**它在任何目录下都生效**。你以后可能从别的地方跑 `ansible` / `ansible-inventory`，配置跟着人走比跟着目录走省心。

> **📖 一段历史，值得知道**（因为它是本方案改版的原因）
>
> 最初的写法是把 `ansible.cfg` 放在**仓库里**（`deploy/ansible/ansible.cfg`）。那样会撞上这个：
>
> ```
> [WARNING]: Ansible is being run in a world writable directory
>            (/mnt/c/.../deploy/ansible), ignoring it as an ansible.cfg source.
> ```
>
> 仓库在 `/mnt/c` 下，而 **WSL 挂载 Windows 盘时权限一律是 `777`**，Ansible 以安全为由**拒绝加载世界可写目录里的配置**。
>
> **最阴的地方是「ignoring it」**——它不是说配置写错了，而是**整个文件被跳过**。你会以为配置生效了，其实一条都没生效（inventory 路径、`host_key_checking` 全部无效）。
>
> 这个根因咬了两次：
>
> | 被咬的地方 | 解法 |
> |---|---|
> | SSH 私钥（阶段一 B） | 密钥生成在 WSL 家目录 |
> | `ansible.cfg` | 配置移到 `~/.ansible.cfg` |
>
> **最终的解法是釜底抽薪**：整个 Ansible 目录搬到 `~/ansible`（见 4.1），跟 `/mnt/c` 彻底脱钩。
>
> **规律记住**：凡是需要 Linux 按权限规则去读/写的东西，都别放 `/mnt/c` 下。

写入 `~/.ansible.cfg`：

```bash
cat > ~/.ansible.cfg <<'EOF'
[defaults]
# inventory 用 ~/ 展开，这样在任何目录下跑 ansible 都能找到
inventory           = ~/ansible/inventory.ini
host_key_checking   = False
retry_files_enabled = False
stdout_callback     = default
result_format       = yaml
EOF

chmod 644 ~/.ansible.cfg
```

> **`host_key_checking = False` 是图省事**。更规范的做法是把服务器指纹写进 `known_hosts`：
> ```bash
> ssh-keyscan -H <你的服务器IP> >> ~/.ssh/known_hosts
> ```
> 这样既能免掉确认提示，又保留了「服务器换了指纹要报警」这层保护。
>
> **`stdout_callback = default` + `result_format = yaml`** 只是让 playbook 输出更好读，纯美观。
>
> **⚠️ 别写成 `stdout_callback = yaml`**（老教程里常见）。2.13 起 `yaml` 变成了一个转发到 `community.general.yaml` 的别名，而那个插件在 `community.general` 12.0.0 里**被删掉了**。于是你现在会看到：
>
> ```
> [ERROR]: The 'community.general.yaml' callback plugin has been removed.
> The plugin has been superseded by the option `result_format=yaml`
> in callback plugin ansible.builtin.default from ansible-core 2.13 onwards.
> ```
>
> 报错里出现的名字（`community.general.yaml`）**和你写的 `yaml` 长得完全不一样**，这就是它难认的地方——那是个已经断掉的转发。**解决办法就是上面这两行**。

**验证配置生效了**——下面这条命令**不带 `-i` 参数**也应该能列出主机：

```bash
cd ~
ansible-inventory --graph
```

期望输出：

```
@myblog:
  |--myblog-server
```

**如果又出现 `world writable` 警告，说明文件没写到 `~` 下。**

> **配置搜索顺序**（记一下，排障用得上）：
> 1. `$ANSIBLE_CONFIG` 环境变量
> 2. 当前目录的 `ansible.cfg` ← **被忽略的那个**
> 3. `~/.ansible.cfg` ← **我们用的**
> 4. `/etc/ansible/ansible.cfg`

### 4.3 文件 2：`~/ansible/inventory.ini`

```ini
[myblog]
myblog-server ansible_host=<你的服务器IP> ansible_user=root ansible_port=22 ansible_ssh_private_key_file=~/.ssh/myblog_deploy

[myblog:vars]
# ★ 阶段一 F 节装的 Python 3.9；不写死的话自动探测会找到 3.6
ansible_python_interpreter=/usr/bin/python3.9
```

**把 `<你的服务器IP>` 换成真实 IP。**

> **⚠️ 这里有个 INI 语法坑，必须单独说。**
>
> 一个很自然、但**完全错误**的写法是「主机名 + 换行缩进」：
>
> ```ini
> # ❌ 这样写是错的
> myblog-server ansible_host=1.2.3.4
>               ansible_user=root
>               ansible_port=22
> ```
>
> **Ansible 的 INI inventory 不支持这种续行。** 它会把每一行都当成一个**独立的主机名**，于是报错长这样：
>
> ```
> ansible_user=root | UNREACHABLE!
> ansible_port=22   | UNREACHABLE!
> ```
>
> 变量被当成主机名去解析了。**更阴险的是**：真正的主机因此**没拿到用户名和私钥路径**，Ansible 会退回到默认值（当前 Linux 用户名 + 默认密钥），于是你看到一个**完全不相关的报错**：
>
> ```
> huhaohua@8.134.254.88: Permission denied (publickey,...)
> ```
>
> 用户名是 `huhaohua` 而不是 `root` —— 这个细节就是线索。
>
> **正确写法有两种**（本文用第一种）：
>
> ```ini
> # 写法一：变量全写在一行（最常用）
> myblog-server ansible_host=1.2.3.4 ansible_user=root
>
> # 写法二：拆成 :vars 段落（变量多了更整齐，但对整组生效）
> [myblog:vars]
> ansible_user=root
> ```
>
> **★ 验证解析对不对**（这一步能提前抓住这类问题，养成习惯）：
>
> ```bash
> ansible-inventory --graph
> ```
>
> 期望输出：
>
> ```
> @myblog:
>   |--myblog-server
> ```
>
> **如果看到 `ansible_user=root` 之类的东西出现在主机列表里，就是这个坑。**

### 4.5 文件 4：`~/ansible/group_vars/all/vault.yml`（★ 加密的密钥）

这个文件**不要用编辑器直接创建**，用 `ansible-vault` 生成，它会提示你设一个 Vault 密码：

```bash
cd ~/ansible
ansible-vault create group_vars/all/vault.yml
```

**记牢这个 Vault 密码**，每次跑 playbook 都要输。然后在打开的编辑器里填入：

```yaml
---
vault_mysql_password: "博客账号 myblog 的密码，自己设一个强密码"
vault_redis_password: "Redis 密码，纯字母数字，跟上面不同"
vault_jwt_secret: "用 openssl rand -base64 48 生成，必须 ≥32 字符"
vault_admin_init_password: "admin 初始密码，必须是强密码"

vault_oss_endpoint: ""
vault_oss_access_key_id: ""
vault_oss_access_key_secret: ""
vault_oss_bucket_name: ""
vault_oss_domain: ""
```

**注意**：这里**不需要** `myapp-mysql` 的 root 密码（见 1.4 的说明）。

生成 JWT 密钥：

```bash
openssl rand -base64 48
```

> **Vault 的价值**：这个文件加密后**可以安全地提交进 Git**。你以后回看历史，也能知道"当时线上是什么配置"，而密钥本身是密文。这就是「配置即代码」的核心。
>
> 想改内容用 `ansible-vault edit group_vars/all/vault.yml`，想看明文用 `ansible-vault view group_vars/all/vault.yml`。

### 4.6 文件 5：`~/ansible/site.yml`

```yaml
---
# ========== 第一步：前置检查（失败就立刻停，给你清楚的报错）==========
- name: 部署前置检查
  hosts: myblog
  gather_facts: false
  tasks:
    - name: 检查 Docker 是否可用
      ansible.builtin.command: docker --version
      changed_when: false

    - name: 检查网络 {{ myapp_network }} 是否存在（另一个项目建的）
      ansible.builtin.command: "docker network inspect {{ myapp_network }}"
      changed_when: false

    - name: 检查容器 {{ mydb_container }} 是否在运行
      ansible.builtin.command: >-
        docker inspect -f {% raw %}{{.State.Running}}{% endraw %} {{ mydb_container }}
      changed_when: false
      register: db_running
      failed_when: "'true' not in db_running.stdout"

    - name: 检查另一个项目的 tlias 库存在（后面要确认没被影响）
      ansible.builtin.shell: >-
        docker exec -i {{ mydb_container }} sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N -e "show databases;"'
      changed_when: false
      register: before_dbs
      failed_when: "'tlias' not in before_dbs.stdout"
      no_log: true

# ========== 第二步：正式初始化 ==========
- name: 初始化博客服务器
  hosts: myblog
  roles:
    - docker
    - myblog-init
```

### 4.7 文件 6：`~/ansible/roles/docker/tasks/main.yml`

```yaml
---
- name: 创建 /etc/docker 目录
  ansible.builtin.file:
    path: /etc/docker
    state: directory
    mode: "0755"

- name: 备份最初的 daemon.json（只在首次执行时备份）
  ansible.builtin.copy:
    src: /etc/docker/daemon.json
    dest: /etc/docker/daemon.json.orig
    remote_src: true
    force: false          # 已存在就不覆盖，保护最初的版本
  failed_when: false

- name: 配置 Docker 镜像加速与日志轮转
  ansible.builtin.template:
    src: daemon.json.j2
    dest: /etc/docker/daemon.json
    mode: "0644"
  notify: 重启 docker

- name: 预拉基础镜像（首次较慢，之后直接命中缓存）
  ansible.builtin.command: "docker pull {{ item }}"
  loop: "{{ base_images }}"
  register: pull_result
  changed_when: "'Status: Downloaded newer image' in pull_result.stdout"
```

### 4.8 文件 7：`~/ansible/roles/docker/handlers/main.yml`

```yaml
---
- name: 重启 docker
  ansible.builtin.systemd:
    name: docker
    state: restarted
```

> **handler 是 Ansible 的精华之一**：它只在「配置真的变了」的时候才触发。第一次跑会重启 Docker，第二次跑因为 `daemon.json` 内容没变，**不会重启**——这就是幂等。

> ### ⚠️ 这个 handler 是本方案里**唯一会碰到另一个项目**的地方
>
> **`systemctl restart docker` 会重启整台机器上的 Docker 守护进程——所有容器一起停、一起起，包括 `myapp-frontend` / `myapp-backend` / `myapp-mysql`。**
>
> 之前所有步骤都严格绕开了另一个项目，只有这一步绕不开：`daemon.json` 改了必须重启 Docker 才生效。
>
> 停下来的容器**会不会自己回来，取决于它自己的重启策略**：
>
> | 策略 | 重启后 | 后果 |
> |---|---|---|
> | `unless-stopped` / `always` | ✅ 自动拉起 | 只是几十秒的服务中断 |
> | `no` / `on-failure` | ❌ **不回来** | **另一个项目静默挂掉**，你得手动起 |
>
> **★ 真跑之前必须查一遍**（在服务器上）：
>
> ```bash
> docker inspect -f '{{.Name}} restart={{.HostConfig.RestartPolicy.Name}}' $(docker ps -q)
> ```
>
> - 全是 `unless-stopped` / `always` → 可以放心跑，顶多几十秒中断
> - **有 `no` 的 → 先想清楚那个容器怎么恢复**，别让它默默挂掉
>
> **跑完之后立刻验证另一个项目**（验收清单第 7 项）——这正是那一条存在的意义。

#### 三个必须理解的配置项

**① `ADMIN_INIT_PASSWORD` 必须第一次就填对**

看 `myblog-user/myblog-user-impl/src/main/java/com/myblog/user/config/AdminInitializer.java` 的逻辑：它只在数据库里**不存在** `admin` 用户时才创建账号，已存在就直接 return。

所以：**第一次启动前没设这个变量 → 系统会用默认弱密码 `admin123` 建出 admin 账号**，之后每次启动都不会再改（也不会重置你后来手动改的密码）。

**② `SPRING_PROFILES_ACTIVE=prod` 为什么写在 `.env` 而不是改代码**

`bootstrap/src/main/resources/application.yml` 第 14 行硬编码了 `active: dev`。但**环境变量优先级高于配置文件**，所以在 `.env` 里设 `SPRING_PROFILES_ACTIVE=prod` 就能切过去，**不用改任何一行代码**。prod profile 会关掉 Knife4j 接口文档（见 `application-prod.yml`）。

**③ 为什么用 `env_file` 而不是挂载 `.env` 文件**

`application.yml` 第 16 行是 `spring.config.import: optional:file:./.env[.properties]`——它按**运行工作目录**找文件。容器里工作目录是 `/app`，路径很容易错位。用 Docker Compose 的 `env_file` 让密钥变成**真正的环境变量**，优先级更高，Spring Boot 能直接认 `MYSQL_HOST` 这类名字。

## 5. 阶段三：项目里要建的 5 个文件

> 这一阶段在**你自己的电脑上**操作。这 5 个文件是**每次发布**要用的，CI 首次运行时会自动传到服务器。

### 文件 1：`deploy/backend/Dockerfile`

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
ENV TZ=Asia/Shanghai
COPY app.jar app.jar
EXPOSE 8080
# JAVA_OPTS 从 .env 注入，方便在小内存服务器上调堆大小

```

> 服务器上**不需要装 JDK 和 Maven**。编译在 GitHub 上做完了，服务器只负责把 jar 塞进 JRE 镜像里跑起来。

### 文件 2：`deploy/docker-compose.yml`

```yaml
services:
  backend:
    build: ./backend
    image: myblog-backend:latest
    container_name: myblog-backend
    restart: unless-stopped
    env_file: [.env]
    mem_limit: 512m
    volumes:
      - ./logs:/app/logs
    depends_on:
      redis:
        condition: service_healthy
    networks:
      - myblog
      - myapp_net          # ★ 为了能按名字访问 myapp-mysql

  redis:
    image: redis:7-alpine  # 服务器本地已有这个镜像，不用重新拉
    container_name: myblog-redis
    restart: unless-stopped
    environment:
      REDIS_PASSWORD: ${REDIS_PASSWORD}
    # 内存上限 80m + LRU 淘汰：缓存涨起来也不会把服务器拖垮
    command: >
      sh -c 'redis-server --requirepass "$$REDIS_PASSWORD"
             --appendonly yes --maxmemory 80mb --maxmemory-policy allkeys-lru'
    healthcheck:
      # REDISCLI_AUTH 是 redis-cli 官方推荐的传密码方式，避免密码出现在命令行参数里
      test: ["CMD-SHELL", "REDISCLI_AUTH=$$REDIS_PASSWORD redis-cli ping | grep -q PONG"]
      interval: 5s
      timeout: 3s
      retries: 10
    mem_limit: 96m
    volumes:
      - ./redis-data:/data
    networks: [myblog]

  nginx:
    image: nginx:alpine
    container_name: myblog-nginx
    restart: unless-stopped
    ports:
      - "8081:80"          # ★ 公网入口；80 被 myapp-frontend 占着
    volumes:
      - ./frontend/dist:/usr/share/nginx/html:ro
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [backend]
    mem_limit: 64m
    networks: [myblog]

networks:
  myblog:
    name: myblog_net
  myapp_net:
    name: myapp_app-network
    external: true         # ★ 另一个项目已经建好的网络，我们只加入、不创建
```

#### 四个设计点

**① backend 不发布任何端口**
原方案里给它绑了 `127.0.0.1:8080`，但你的 8080 被 `myapp-backend` 占了（而且它是 `0.0.0.0` **全公网暴露**的——那是安全隐患，见 10.4）。博客的 CI 冒烟测试走 Nginx 就够了。

**② `external: true` 的含义**
表示 `myapp_app-network` 是**别的项目建的**，我们只加入、不创建。所以**绝不能删这个网络**，也别在 `/opt/myblog` 下执行 `docker compose down -v`。

**③ Redis 健康检查**
backend 依赖它 `service_healthy` 才启动。否则 Redis 没起来时后端起不来，`restart: unless-stopped` 会让它反复重启，日志刷屏还找不到原因。

**④ `$$REDIS_PASSWORD` 里为什么是两个 `$`**
compose 文件里 `$` 是变量插值符号，写 `$$` 是转义，让 Docker Compose 把它当**字面量 `$`** 传给容器，再由容器里的 `sh` 展开。这是 Compose 的标准写法。

### 文件 3：`deploy/nginx/default.conf`

```nginx
server {
    listen 80;
    server_name _;                      # 没域名，用 IP:8081 直连
    root /usr/share/nginx/html;
    index index.html;

    # ★ 图片上传：nginx 默认只放行 1MB，超了直接 413 拒掉，请求根本到不了后端。
    #   前端拦截器把非 401 的错误一律显示成「网络异常」，所以看起来像网络故障。
    #   10m 跟 spring.servlet.multipart.max-file-size 对齐。
    client_max_body_size 10m;

    # ★ 前端是 history 路由，没这行刷新子页面会 404
    location / {
        try_files $uri $uri/ /index.html;
    }

    # ★ 关键：容器重建后 IP 会变，没这行重新部署后必然 502
    resolver 127.0.0.11 valid=10s ipv6=off;
    set $backend http://backend:8080;

    location /api/ {
        proxy_pass $backend$request_uri;   # 保留完整路径（后端 context-path 就是 /api）
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 前端产物带 hash，长缓存；index.html 不缓存，避免发版后拿到旧页面
    location ~* \.(js|css|png|jpg|jpeg|gif|svg|woff2?|ttf|ico)$ {
        expires 30d;
        add_header Cache-Control "public, immutable";
    }
    location = /index.html {
        add_header Cache-Control "no-cache";
    }
}
```

#### 两个 `★` 注释千万别删

**① `try_files $uri $uri/ /index.html;` —— 管「刷新页面 404」**

前端用的是 **history 路由**（`myblog-frontend/src/router/index.js` 第 99 行 `createWebHistory()`）。不加这行，直接访问或刷新 `/archive`、`/admin/dashboard` 这类子路径会 404——因为服务器上并不存在这些路径对应的文件。

**② `resolver 127.0.0.11` + `set $backend` —— 管「重新部署后 502」**

Docker 容器重建后 IP 会变，而 Nginx 默认只在**启动时**解析一次域名并把 IP 缓存住。结果是**每次重新部署后稳定 502**，重启 Nginx 才好——新手基本都会卡在这里，而且很难自己找到原因。

`127.0.0.11` 是 Docker 内置 DNS 的地址。这两行让 Nginx 每 10 秒重新解析一次。

> 用变量写法时 `proxy_pass` 不会自动拼接路径，所以要显式带上 `$request_uri` 保留完整原始路径——这正是后端 `context-path: /api` 需要的。

### 文件 4：`deploy/rollback.sh`

```bash
#!/usr/bin/env bash
# 用法：服务器上执行 bash /opt/myblog/rollback.sh
set -e
cd /opt/myblog

```

```yaml
            cp _incoming/docker-compose.yml docker-compose.yml
            cp _incoming/nginx/default.conf nginx/default.conf
            cp _incoming/rollback.sh        rollback.sh
            chmod +x rollback.sh
            rm -rf _incoming

            # 3) 重建启动（不含 mysql —— 那是另一个项目的）
            docker compose build backend
            docker compose up -d backend redis nginx
            docker compose restart nginx     # 让 nginx 重新解析 backend 的 IP

            # 4) 冒烟测试：走 nginx 的 8081，验证整条链路
            echo "等待后端启动..."
            for i in $(seq 1 30); do
              if curl -fsS http://127.0.0.1:8081/api/config/all >/dev/null 2>&1; then
                echo "✅ 冒烟测试通过"; exit 0
              fi
              sleep 3
            done

            echo "❌ 冒烟测试失败，最近 50 行日志："
            docker compose logs --tail=50 backend
            exit 1
```

> **★ 上面这个代码块只是快照，权威版本永远是仓库里的 [`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml)。**
> 同一份内容存两处，改一处忘一处就会漂移——2026-10-07 首次部署时正是栽在这上面：workflow 里有两个 bug 修好了，这份文档里还留着旧的错版本。**以后改 workflow 请直接改文件，别只改文档。**

> **注意**：`sql/init.sql` 已经由 **Ansible** 负责（见 4.10），所以这里不再重复传。

#### 三个设计点

**① 为什么先传到 `_incoming` 暂存目录**
如果直接覆盖，就没法在覆盖前备份旧版本，回滚功能就废了。流程是：**先传暂存 → 备份旧的 → 换新的 → 重建**。

**② 为什么冒烟测试打 `/api/config/all`**
这是 `ConfigController` 的**前台公开接口**，不需要登录，而且会**真的查数据库**。项目里**没有引入 actuator**（父 pom 和 `bootstrap/pom.xml` 都没有 `spring-boot-starter-actuator`），没有 `/actuator/health` 可用。用真实业务接口当健康检查反而更准——它通了，说明 **Nginx + 后端 + MySQL 三条链路全都活着**。

**③ `concurrency` 的作用**
防止你连续 push 两次导致两个部署同时改服务器文件。`cancel-in-progress: false` 表示排队而不是取消。

## 6. 阶段四：配置 GitHub Secrets

仓库 → **Settings → Secrets and variables → Actions → New repository secret**，加 4 个：

| Name | Value |
|---|---|
| `SERVER_HOST` | 服务器公网 IP |
| `SERVER_USER` | `root` |
| `SERVER_PORT` | `22` |
| `SERVER_SSH_KEY` | 部署私钥的**完整内容** |

> **⚠️ Secret 的名字没有任何规定——别照抄别人教程里的截图。**
>
> `${{ secrets.XXX }}` 里写什么名字，你就得配一个**同名**的。名字对不上，CI 里拿到的就是空字符串，报错还很难懂（认证失败、连接超时）。**以 workflow 里引用的是什么为准。**
>
> 常见疑惑：别人的教程里还有 `PASSWORD` / `TOKEN`，要不要配？
>
> | 别人的 secret | 为什么本方案不需要 |
> |---|---|
> | `PASSWORD` | 那是**密码登录 SSH** 的方案。本方案用**密钥登录**，所以只要 `SERVER_SSH_KEY`，不要密码 |
> | `TOKEN` | GitHub **自带** `secrets.GITHUB_TOKEN`，每个 workflow **自动注入**，不需要手动配。别人自己起的 `TOKEN` 一般是访问别的仓库或镜像仓库用的 |
>
> | | 密码登录 | 密钥登录（★ 本方案） |
> |---|---|---|
> | 需要配 | `PASSWORD` | `SSH_KEY`（私钥全文） |
> | CI 里还要 | 装 `sshpass`，或用 action 的 `password` 参数 | 无 |
> | 风险 | 可被暴力破解、密码容易进日志和历史 | 文件级凭据；GitHub 加密存储并自动打码 |
>
> **所以：本方案只需要 4 个，一个都不多。**

在 **WSL** 里把私钥送进 Windows 剪贴板（`clip.exe` 在 WSL 里直接可用，是 WSL 提供的 Windows 互操作）：

```bash
cat ~/.ssh/myblog_deploy | clip.exe
```

然后直接在 GitHub 的 Value 框里 `Ctrl+V`。

**粘贴后检查两件事**：

1. **必须包含**首行 `-----BEGIN OPENSSH PRIVATE KEY-----` 和末行 `-----END OPENSSH PRIVATE KEY-----`。少一行 CI 就报认证失败。
2. 末尾要有一个**换行**。`clip.exe` 一般会带上；如果 CI 报 `invalid format`，回来看一眼是不是被截断了。

> **如果 `clip.exe` 不可用**（某些终端环境），退而求其次：
> ```bash
> cat ~/.ssh/myblog_deploy
> ```
> 然后用鼠标选中输出、`Ctrl+Shift+C` 复制。

## 8. 回滚

### 什么情况用

线上出问题（页面白屏、接口 500、登录不上），而你需要**立刻恢复**而不是「等修好再发一版」。

### 怎么用

```bash
ssh -i ~/.ssh/myblog_deploy root@<你的服务器IP>
bash /opt/myblog/rollback.sh
```

脚本做四件事：把 `app.jar.prev` 恢复成 `app.jar`、把 `dist.prev` 恢复成 `dist`、重建容器、冒烟测试。

### 它能回退多远

**只有一版**。每次部署会覆盖 `.prev`。

### 前提

服务器上有 `app.jar.prev`（即**至少成功部署过一次**）。从没部署过会提示「❌ 没有可回滚的后端版本」。

### 环境配置怎么回滚

回滚脚本只管**代码制品**。如果问题出在 `.env` 或系统配置上：

```bash
cd ~/ansible
git log --oneline group_vars/all/vault.yml    # 找到上个版本
git checkout <commit> -- group_vars/all/vault.yml
ansible-playbook site.yml --ask-vault-pass    # 重新应用
```

这正是「配置进 Git」的价值——**环境和代码一样可以回滚**。

## 9. 最容易踩的坑

### ① 刷新子页面 404
**现象**：首页正常，但访问/刷新 `/archive`、`/admin/dashboard` 报 404。
**原因**：Nginx 缺 `try_files` 回退，前端是 history 路由。
**解决**：文件 3 里已含，别删。

### ② 重新部署后稳定 502
**现象**：部署成功、冒烟测试也过了，但访问几次就 502。
**原因**：Nginx 缓存了 backend 容器的旧 IP，容器重建后 IP 变了。
**解决**：文件 3 里的 `resolver` + `set $backend`；deploy 脚本里的 `docker compose restart nginx`。两处都在，别删。

### ③ admin 密码成了 `admin123`
**现象**：用 `admin123` 能登进去。
**原因**：第一次启动前没设 `ADMIN_INIT_PASSWORD`（Vault 里没填）。
**解决**：改 Vault → 重跑 Ansible **不够**（密码只在账号不存在时设置）。需要先删掉 `sys_user` 里的 admin 记录，再重启后端让它重新初始化。

### ④ 外网打不开 `http://<IP>:8081`
**现象**：服务器上 `curl http://127.0.0.1:8081` 正常，外面访问不了。
**原因**：阿里云安全组没放行 8081。
**解决**：控制台 → 安全组 → 入方向 → 添加 8081。

### ⑤ Ansible 报 Python 版本错误
**现象**：模块传输成功，但执行时报 `SyntaxError: future feature annotations is not defined`。
**原因**：CentOS 8 的系统 Python 是 **3.6**，而新版 Ansible 生成的模块要求 ≥3.7。
**解决**：按 **阶段一 F 节**修好 yum 源并装 `python39`，再把 inventory 里改成 `/usr/bin/python3.9`。
（降级本地 Ansible 到 `<2.17` 也行，但 CentOS 8 的源迟早要修，不如一次做完。）

### ⑥ `world writable directory` 警告 —— 配置文件被静默忽略
**现象**：
```
[WARNING]: Ansible is being run in a world writable directory (...), ignoring it as an ansible.cfg source.
```
**原因**：仓库在 `/mnt/c` 下，WSL 挂载 Windows 盘权限一律 `777`。Ansible 拒绝加载世界可写目录里的配置。
**危险点**：**它只是 warning 不是 error**，你会以为配置生效了，其实**一条都没生效**（inventory 路径、host_key_checking 全部无效）。
**解决**：配置放 `~/.ansible.cfg`（见 4.2），并且整个 Ansible 目录搬到 `~/ansible`，跟 `/mnt/c` 脱钩（见 4.1）。

> **同一个根因咬了两次**：SSH 私钥（阶段一 B）和 `ansible.cfg`（4.2）。
> **规律**：凡是需要 Linux 按权限规则去读/写的东西，都别放 `/mnt/c` 下。
> **根治**：别跨 Windows/Linux 边界工作——Linux 的活就在 Linux 文件系统里干。

### ⑦ inventory 里的变量被当成了主机名
**现象**：
```
ansible_user=root | UNREACHABLE!
ansible_port=22   | UNREACHABLE!
```
甚至可能连带出现一个**看起来毫不相关**的报错：
```
huhaohua@<服务器IP>: Permission denied (publickey,...)
```
**原因**：INI inventory **不支持换行续写**。写成「主机名 + 换行缩进」时，每一行都被当成独立主机名；真正的主机因此**没拿到用户名和私钥**，Ansible 退回默认值（当前 Linux 用户 + 默认密钥）→ 认证失败。
**线索**：报错里的用户名是 `huhaohua` 而不是 `root`。
**解决**：变量**全写在一行**（见 4.3）。
**预防**：改完 inventory 先跑 `ansible-inventory --graph`，确认主机列表里**只有真正的主机**。

### ⑧ 拉不动基础镜像
**现象**：Ansible 拉镜像任务失败，日志里有 `timeout`。
**原因**：国内网络拉不到 Docker Hub。
**解决**：`group_vars/all/main.yml` 里的 `docker_registry_mirrors` 填当前可用的加速地址。

### ⑨ `.env` 里 `MYSQL_HOST` 填了 `localhost`
**现象**：后端启动失败，报连不上数据库。
**原因**：容器里的 `localhost` 指的是**容器自己**。
**解决**：模板里已写成 `{{ mydb_container }}`（即 `myapp-mysql`），靠 `myapp_app-network` 解析。

### ⑩ 内存爆
**现象**：`docker stats` 里 backend 接近 512m 上限，或容器被 OOM Kill 反复重启。
**解决**：调小 `env.j2` 里的 `-Xmx300m`（比如 `-Xmx220m`），重跑 Ansible + `docker compose up -d backend`。
**根本方案**：升级到 2核4G（见 10.3）。

### ⑪ `ansible-playbook` 一启动就报 callback plugin 被移除
**现象**：
```
[ERROR]: The 'community.general.yaml' callback plugin has been removed.
The plugin has been superseded by the option `result_format=yaml`
in callback plugin ansible.builtin.default from ansible-core 2.13 onwards.
This feature was removed from collection 'community.general' version 12.0.0.
```
**原因**：`~/.ansible.cfg` 里写了 `stdout_callback = yaml`。2.13 起 `yaml` 只是个转发到 `community.general.yaml` 的别名，而该插件在 `community.general` 12.0.0 被删除，转发**断了**。
**难点**：报错里的名字和你写的完全对不上（你写 `yaml`，它说 `community.general.yaml`），不看解释很难联想到是配置那行。
**解决**：改成两行——
```ini
stdout_callback = default
result_format   = yaml
```
**注意**：这是**启动阶段**的硬错误，playbook 一行都没执行。看到它别去查 playbook，问题在配置。

### ⑫ `'vault_xxx' is undefined` —— vault 文件没被加载
**现象**：playbook 跑得好好的，到某个用到密钥的任务突然炸：
```
Error while resolving value for 'stdin': 'vault_mysql_password' is undefined
```
**原因（两个，都要查）**：
1. **文件名叫错**——最常见。`group_vars/all.vault.yml` 会让 Ansible 认为组名是 `all.vault`，没有这个组，**静默跳过**。必须用目录形式 `group_vars/all/vault.yml`（见 4.1）。
2. 文件确实还没创建。

**为什么难查**：报错出现在**使用变量**的地方，跟**文件名**隔着十万八千里。而且它不报「文件找不到」，只是变量为空。
**解决**：按 4.1 改成目录形式，然后验证：
```bash
cd ~/ansible
ansible myblog -m debug -a 'msg="vault_mysql_password defined: {{ vault_mysql_password is defined }}"' --ask-vault-pass
```
看到 `defined: True` 就对了。
**顺带一提**：`--ask-vault-pass` 提示你输密码并**不代表**有文件被解密——没有加密文件时它照样问你。**别把「密码输进去了」当成「文件加载了」。**

## 10. 后续事项

### 10.1 CentOS 8 已停止维护

`CentOS Linux 8` 在 **2021 年 12 月 31 日 EOL**，官方 yum 源已下线。

**阶段一 F 节已经把源修好了**（指向阿里云归档站）——所以你以后 `dnf install` 是能用的，不用再担心。

**但要注意归档站的性质**：`vault` 是**只读快照**，只有 CentOS 8 停止维护那一刻的包，**不会再有安全更新**。

所以：

- ✅ 装东西没问题（`python39`、`vim`、`htop`……都能装）
- ❌ **拿不到任何安全补丁**。这台机器跑在公网上，长期裸奔是真实风险

**长期方案**：重装成 **Rocky Linux 9** 或 **Ubuntu 22.04**（阿里云控制台可以更换系统盘）。
**短期**：Ansible playbook 里**刻意没有用任何 `yum`/`dnf` 任务**——部署本身不依赖包管理器，所以即使源彻底挂掉，你的 CI/CD 也不受影响。

### 10.2 加 HTTPS（等有域名之后）

1. 域名解析到服务器 IP
2. 在 `deploy/nginx/default.conf` 里加一个 80→443 跳转的 server 块
3. 用 certbot 自动签发 + 续期

**改动集中在 `default.conf` 一个文件，Ansible 和 CI 都不用动。**

### 10.3 升级服务器内存（建议尽早）

这台机器 2核1.7G，用完只剩 ~340 MiB 余量。风险在于**两个项目共享同一台机器的内存**——另一个项目哪天内存涨一点，或者博客来了一波流量，就可能互相挤到 OOM。

**建议升到 2核4G**。升级后可以：

- 放宽 JVM 堆：`-Xmx300m` → `-Xmx1g`（改 `env.j2` 后重跑 Ansible）
- 有余力的话给博客配独立 MySQL 容器，彻底解耦

### 10.4 另一个项目的安全建议（顺手提一下）

`myapp-backend` 是 `0.0.0.0:8080->8080`，**8080 端口对整个公网开放**。任何人都能绕过它的 Nginx 直接打后端接口。建议改成 `127.0.0.1:8080->8080`，然后让它的 Nginx 反代过去。

### 10.5 下一步学什么

CI/CD 和 Ansible 跑通之后，**日志、监控、告警、故障演练**这些在本地虚拟机上练全套 → 见配套文档 `运维练习方案.md`。
