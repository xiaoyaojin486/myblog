# 数据库备份与恢复手册

> 配套文件：
>
> - [deploy/backup.sh](backup.sh) —— 每日备份脚本（CI 投递到 `/opt/myblog/backup.sh`）
> - [deploy/backup-restore-check.sh](backup-restore-check.sh) —— 恢复演练脚本
> - [deploy/ansible/roles/myblog-backup/](ansible/roles/myblog-backup/) —— 主机侧配置（ossutil、凭据、systemd 定时器）

## 1. 这套备份长什么样

```
每天 03:17  云服务器（systemd timer，24×7，错过会补跑）
   │
   ├─ docker exec myblog-mysql mysqldump --single-transaction
   │       │
   │       └─ gzip ──► /opt/myblog/backup/myblog-YYYYmmdd-HHMM.sql.gz   ← 副本② 本地
   │                          │
   │                          ├─ 校验：gzip -t + 大小 + 数一下有没有建表语句
   │                          │
   │                          ├─ ossutil cp ──► oss://<备份桶>/daily/…   ← 副本③ 异地
   │                          │
   │                          ├─ 删掉 7 天前的本地文件
   │                          │
   │                          └─ touch status/last_success  ← 心跳文件，监控盯它
```

### 两份副本分别防什么（面试必问）

| 副本   | 位置                  | 保留  | 防得住                                      | **防不住**                      |
| ------ | --------------------- | ----- | ------------------------------------------- | ------------------------------- |
| ② 本地 | `/opt/myblog/backup/` | 7 天  | 误删、误操作、程序 bug 写坏数据、改错表结构 | ⚠️ **磁盘坏了、整台服务器没了** |
| ③ 异地 | 阿里云 OSS            | 30 天 | 上面全部 **+ 服务器整个没了**               | —                               |

> **说句实话**：本地那份和源数据在**同一块盘**上（这台机器只有一块盘）。
> 所以它防的是「手滑」这类事故 —— 也就是 2026-10-10 那次。
> **真正扛灾难的是 OSS 那份。** 两者不是重复，是分工。

### 两个关键数字

- **RPO ≈ 24 小时** —— 每天备份一次，最坏情况丢掉最近一天的数据。
  （`Persistent=true` 保证了「机器没开机」不会让某天静默少一份）
- **RTO ≈ 15 分钟** —— 见第 8 节，从零到博客能访问。

## 2. ★ 第一步：建桶和钥匙（手动做，一次就好）

### 2.1 建备份专用桶

OSS 控制台 → **Bucket 列表（Bucket List）** → **创建 Bucket（Create Bucket）**

| 字段                       | 填什么                                                         | 为什么                                                                        |
| -------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Bucket 名称（Bucket Name） | 例如 `myblog-backup-xxx`（全局唯一，只能小写字母/数字/短横线） | 名字全局唯一，被占了就换一个                                                  |
| 地域（Region）             | ★ **必须和你的 ECS 同一个地域**                                | 同地域走阿里云**内网**，上传流量**不计费**；跨地域要走出网流量，**要花钱**    |
| 存储类型（Storage Class）  | **标准存储（Standard）**                                       | 备份要能立刻读回来，低频/归档类型取回要等                                     |
| 读写权限（ACL）            | ★ **私有（Private）**                                          | 备份桶绝不开公共读 —— 图片桶那个坑别再踩一次                                  |
| 版本控制（Versioning）     | ★ **不开**                                                     | 我们靠「文件名带时间戳 + 账号没有删除权」防篡改；开了版本控制只会让存储量翻倍 |
| 服务端加密                 | 不用开                                                         | 备份本身已 gzip，桶又是私有的                                                 |

> **为什么单开一个桶，而不是在现有桶里加个目录？**
> 因为 `hu-tlias` 那个桶是和另一个项目**共用**的 —— 那正是 10-10 删库事故的根源。
> 备份的意义就是「独立于故障域」。放进同一个桶，等于把备胎和轮胎挂在同一个钉子上。

### 2.2 加保留策略：30 天后自动过期

进桶 → **数据管理（Data Management）** → **生命周期（Lifecycle）** → **创建规则（Create Rule）**

| 字段                       | 填什么                                |
| -------------------------- | ------------------------------------- |
| 规则名称                   | `expire-backup-30d`                   |
| 生效范围（Prefix）         | 留空（整桶）或 `daily/`               |
| **过期删除（Expiration）** | 选「**对象最后修改时间**」→ **30 天** |

> ⚠️ **这一步最容易选错。** 下拉里有两个长得很像的动作：
>
> | 动作                 | 删的是                        | 备份桶要哪个  |
> | -------------------- | ----------------------------- | ------------- |
> | **历史版本**文件过期 | 被覆盖/删除后留下的**旧版本** | ❌ 不是这个   |
> | **当前版本**过期     | **文件本身**                  | ✅ **是这个** |
>
> 选错了规则就形同虚设（这个桶没开版本控制，压根没有「历史版本」可删）。

### 2.3 建 RAM 子账号 + 最小权限策略

**这一步是整个方案里最值钱的地方。**

RAM 控制台 → **身份管理（Identities）** → **用户（Users）** → **创建用户（Create User）**

| 字段                   | 填什么                                                                          |
| ---------------------- | ------------------------------------------------------------------------------- |
| 登录名称（Logon Name） | `myblog-backup`                                                                 |
| 访问方式               | ★ **只勾「OpenAPI 调用访问」（Programmatic access）**，**不要勾「控制台访问」** |

> 为什么不给控制台访问：这个账号只给脚本用，**它不需要能登录网页**。
> 少一条登录路径，就少一个被撞库的入口。

创建完成后**立刻**保存 AccessKey ID 和 Secret —— **Secret 只显示这一次**，关掉就再也看不到了。

然后：RAM → **权限策略（Policies）** → **创建策略（Create Policy）** → 选 **脚本编辑（Script）**，粘贴：

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:PutObject", "oss:GetObject", "oss:ListObjects"],
      "Resource": ["acs:oss:*:*:<你的备份桶名>", "acs:oss:*:*:<你的备份桶名>/*"]
    }
  ]
}
```

策略名填 `myblog-backup-policy` → 创建 → 回到用户页 → **添加权限（Add Permissions）** → 选这个自定义策略。

**两条 `Resource` 都要写**：

- 桶那条（没有 `/*`）是给 `ListObjects` 用的 —— 列桶里的文件
- `/*` 那条是给 `PutObject` / `GetObject` 用的 —— 读写具体的文件

少一条的典型症状是「上传报错，但错误信息看不出哪里不对」。

#### ★ 为什么故意不给 `oss:DeleteObject`

这是**防篡改备份（immutable backup）**的核心。

备份脚本跑在服务器上。服务器的凭据一旦泄漏 —— 或者哪天脚本里某个变量写错了、路径拼成了桶根目录 —— **一个能删备份的账号，就能在一夜之间把备份全部清空**。那时候你连「回到昨天」的机会都没有。

**没有删除权，最坏情况只是多传了几个没用的文件。**

那过期清理怎么办？—— 交给 **2.2 那条生命周期规则**。清理动作发生在**服务端**，用的是阿里云自己的权限，**跟这个账号一点关系都没有**。

> 客户端删不掉、服务端按规则删 —— 这才叫「备份账号动不了备份」。
>
> ⚠️ 顺便：**也别图省事挂 `AliyunOSSFullAccess`**。那是全账号所有桶的完全控制权，等于没做隔离。

### 2.4 填进 Ansible Vault

四个变量加进 `deploy/ansible/group_vars/all/vault.yml`：

```yaml
vault_oss_backup_endpoint: oss-cn-<你的地域>.aliyuncs.com
vault_oss_backup_bucket: <你的备份桶名>
vault_oss_backup_access_key_id: <AccessKey ID>
vault_oss_backup_access_key_secret: <AccessKey Secret>
```

用 `ansible-vault edit deploy/ansible/group_vars/all/vault.yml` 打开来改。

> ⚠️ **这个文件必须保持加密**。提交前确认第一行还是 `$ANSIBLE_VAULT;1.1;AES256`。
>
> ⚠️ **不复用应用 `.env` 里那套 `OSS_ACCESS_KEY_*`**。让跑在应用容器里的代码看得见备份钥匙，最小权限就白做了。

## 3. 第二步：跑 Ansible

在 WSL2 里：

```bash
cd ~/ansible          # 你的运行目录
ansible-playbook site.yml --ask-vault-pass
```

这一步会做四件事（都是幂等的，重复跑没问题）：

1. 建 `/opt/myblog/backup/`（权限 0700）
2. 下载 `ossutil` 到 `/usr/local/bin/ossutil-1.7.18` + 软链，并**验证它跑得起来**
3. 从 Vault 渲染 `/opt/myblog/backup/ossutil.conf`（0600）
4. 投递 `myblog-backup.service` / `.timer`，并启用定时器

验证：

```bash
systemctl list-timers myblog-backup.timer     # 应该看到下次触发时间
systemctl status myblog-backup.timer
ossutil --version
ls -l /opt/myblog/backup/                     # ossutil.conf 必须是 -rw-------
```

### ★ 先 push 一次：脚本还没上去

到这一步，Ansible 装的只是**环境** —— 目录、ossutil、凭据、systemd 单元。
**`/opt/myblog/backup.sh` 不在里面。**

它不是漏了，是**刻意不归 Ansible 管**：脚本跟 `rollback.sh` 一样，由 CI 随每次 push 投递
（见 §1「这套东西由哪些文件组成」，以及 [新版部署方案.md](新版部署方案.md) §0.5 的分工）。

所以**现在**直接跑备份会失败，报的就是这句：

```
Failed at step EXEC spawning /opt/myblog/backup.sh: No such file or directory
```

**先提交并推送这批改动**（在仓库里，Windows 上）：

```bash
git add <本次要提交的文件>
git commit -m "feat(backup): 数据库每日备份 + 恢复演练 + 心跳监控"
git push
```

**等 GitHub Actions 跑绿**（仓库 → Actions 页看到对勾），再确认脚本到位：

```bash
ls -l /opt/myblog/backup.sh     # 要看到这个文件，并且带 x 权限
```

看到了，才能往下走 §4。

> ⚠️ **这次 push 会触发一次完整部署**：backend / frontend / nginx 容器都会重建，服务短暂重启。
> 这是把脚本送上服务器必须付的代价。
>
> 如果不想现在重启应用，可以先用 `scp` 手工把脚本传上去顶着，等下次正常 push 时 CI 自然接管：
>
> ```bash
> scp deploy/backup.sh <你的服务器>:/opt/myblog/backup.sh
> ssh <你的服务器> 'chmod +x /opt/myblog/backup.sh'
> ```
>
> 传的文件和仓库里一模一样，不会出现「两个版本」。

## 4. 第三步：手工跑一次备份

```bash
systemctl start myblog-backup.service
journalctl -u myblog-backup -n 30 --no-pager
```

**期望输出**（这就是所谓的"结构化日志"，每行一个 `event=`，一眼就是时间线）：

```
event=backup_start db=myblog out=myblog-20261011-0317.sql.gz
event=dump_ok size=152340 tables=12
event=oss_upload_ok
event=backup_ok file=myblog-20261011-0317.sql.gz size=152340 tables=12
```

再确认两份副本都在：

```bash
ls -lh /opt/myblog/backup/*.sql.gz
ossutil -c /opt/myblog/backup/ossutil.conf ls oss://<备份桶>/daily/
```

### ★ 4.1 反过来验一次：确认「防篡改」真的生效

拿备份账号去删一个文件，**必须失败**：

```bash
ossutil -c /opt/myblog/backup/ossutil.conf rm oss://<备份桶>/daily/<随便一个文件>
```

**期望：报 `AccessDenied` 之类的权限错误。**

如果它**删成功了**，说明策略配错了（多半是误挂了 `AliyunOSSFullAccess`）—— 回去查 2.3。

> 这条比"备份成功了"更重要。备份能成功只说明路通了；**删不掉**才说明这个设计真的成立。

### 4.2 确认「脚本失败会真的报错」

```bash
# 故意把 MySQL 停掉，再跑一次 —— 模拟"导出失败"
docker stop myblog-mysql
systemctl start myblog-backup.service
echo "退出码=$?"
journalctl -u myblog-backup -n 10 --no-pager
docker start myblog-mysql

# 记得手工补一次真备份
systemctl start myblog-backup.service
```

**期望**：退出码非 0，日志里是 `event=backup_fail reason=dump_failed`，而且**没有**产生一个空文件、**没有**上传任何东西、**没有**更新心跳。

> 这就是 `set -euo pipefail` + 校验那几步存在的意义：
> **宁可明确失败，也不要产出一个"看起来成功了"的假备份。**

## 5. 第四步：恢复演练

```bash
bash /opt/myblog/backup-restore-check.sh
```

它会：从 **OSS** 拉最新备份 → 解压 → 建一个临时库 `myblog_restore_check` → 导入 → **逐表比对行数** → 销毁临时库 → 再确认生产库一行没变。

**期望结尾**：

```
✅ 恢复演练通过：myblog-20261011-0317.sql.gz 可以真正恢复出完整数据
```

### 为什么必须做这一步

**只备份、不验证恢复 = 没有备份。**

备份里那些致命的问题 —— 导出了空文件、表没导全、gzip 被截断、上传到一半断了 —— **平时完全看不出来**。只有真恢复一次才会暴露，而那时候通常已经晚了。

### 两处刻意的设计

1. **从 OSS 拉，不从本地拉** → 顺带验证了**异地副本真的取得回来**。灾难发生时你只能靠它。
2. **导进临时库，不碰生产库** → 这台机器只剩 468M 内存，单独再起一个 MySQL 容器做演练是撑不住的，所以在现有容器里建临时库。脚本会在演练前后各数一遍生产库行数，**对不上就报错**。

> 这个脚本能导进临时库，靠的是备份时**故意没加 `--databases`**。
> 加了的话文件里会写死 `CREATE DATABASE myblog` / `USE myblog`，就只能覆盖生产库了。

**建议：每个月手工跑一次这个脚本。** 它不占资源、不动生产库，跑一次的成本几乎为零。

## 6. 第五步：心跳监控 —— 盯「有没有发生」，不是「有没有报错」

### 为什么不能只监控脚本报错

| 情况                                       | 监控脚本报错能发现吗            |
| ------------------------------------------ | ------------------------------- |
| 脚本跑了、但 mysqldump 失败                | ✅ 能（退出码非 0）             |
| **定时器挂了 / 机器重启后服务没起来**      | ❌ **不能 —— 压根没有错误可抓** |
| **磁盘满了、备份提前失败**                 | 部分能                          |
| **脚本被改了、逻辑走岔了，但退出码还是 0** | ❌ 不能                         |

最危险的不是"脚本报错"，而是"**脚本根本没跑**"。

所以监控的是 `/opt/myblog/status/last_success` 这个文件的时间戳 —— 它的 mtime 语义是「**最后一次成功备份是什么时候**」。

### 6.1 先给 Zabbix Agent 加挂载

⚠️ **Agent 是跑在容器里的，而现在那个容器一个卷都没挂 —— 它看不见服务器上的文件。**

编辑云服务器上的 `/opt/zabbix-agent/docker-compose.yml`，在 `zabbix-agent` 服务里加：

```yaml
volumes:
  - /opt/myblog/status:/opt/myblog/status:ro
```

然后：

```bash
cd /opt/zabbix-agent
docker compose up -d
docker exec myblog-zabbix-agent ls -l /opt/myblog/status/last_success
# 能列出来就说明挂载生效了
```

#### ★ 为什么挂 `status/` 而不是 `backup/`（这条是踩出来的）

心跳文件一开始放在 `/opt/myblog/backup/.last_success` —— 和备份、凭据挤在一个目录里。那个目录是 **0700**，而 Agent 容器**是以非 root 跑的**（`zabbix` 用户，uid 1997）。结果：

```
ls: cannot access '/opt/myblog/backup/.last_success': Permission denied
```

**卡住的是目录，不是文件。** `.last_success` 自己就是 `0644`、人人可读 —— 但要读一个文件，先得能"穿过"它所在的目录，也就是**目录上得有 `x` 位**，而 `0700` 只给了 root。

> ★ 排查时记住这条：**先看目录权限（`ls -ld`），再看文件权限（`ls -l`）。**
> 一个 0644 的文件照样读不到，只要它的父目录是 0700。
>
> 验证手法：`docker exec -u root …` 能读、不加 `-u root` 读不了 → 就锁定是"身份/权限"，跟挂载无关。

所以做法不是"把 backup 目录放宽"（那会连 OSS 凭据一起暴露），而是**把两种东西分家**：

| 目录                  | 权限   | 里面是什么              | 谁能看                           |
| --------------------- | ------ | ----------------------- | -------------------------------- |
| `/opt/myblog/backup/` | `0700` | OSS 凭据、数据库导出    | 只有 root                        |
| `/opt/myblog/status/` | `0755` | 一个空的 `last_success` | 谁都能看 —— 它本来就是给监控看的 |

Ansible 负责建好这两样（见 role 里的「创建监控状态目录」和「预建心跳文件」）。

### 6.2 建监控项

Web 界面：**Data collection（数据采集）→ Hosts（主机）→ myblog-server → Items（监控项）→ Create item（创建监控项）**

| 字段                                 | 填什么                                           |
| ------------------------------------ | ------------------------------------------------ |
| Name（名称）                         | `备份新鲜度`                                     |
| Type（类型）                         | **Zabbix agent（Zabbix 客户端）**                |
| Key（键值）                          | `vfs.file.time[/opt/myblog/status/last_success]` |
| Type of information（信息类型）      | **Numeric (unsigned)（数字（无正负））**         |
| Update interval（更新间隔）          | `5m`                                             |
| History（历史记录） / Trends（趋势） | `31d` / `365d`（默认值就够）                     |

> ⚠️ `.last_success` 必须**先存在**。文件不存在时这个监控项会变成 unsupported，触发器拿不到值 —— 等于没监控。Ansible 已经替你 precreate 了（见 role 里的「预建心跳文件」）。
>
> 点一下 **Test（测试）** 确认能取到值再往下走。

#### ★ 加一步预处理：把"时间戳"变成"多少秒前"

`vfs.file.time` 取回来的是一个 **Unix 时间戳** —— 一大串数字，比如 `1775091234`。

这东西有两个毛病：**读不出来是什么意思**，而且**没法写触发器阈值**（你没法把"26 小时"翻译成某个固定的时间戳）。

所以在 **Preprocessing（预处理）→ Add（添加）→ Custom script（自定义脚本）** 里加一步：

```javascript
// 'value' 是 Zabbix 传进来的原始时间戳（比如 1775091234）
// Math.floor(Date.now() / 1000) 获取当前时间戳（秒）
// 两者相减，得出"多少秒前"
return Math.floor(Date.now() / 1000) - value;
```

做完之后，这个监控项的值就变成了「**距离上次成功备份过了多少秒**」—— `0` 是刚备份完，`93600` 是 26 小时前。**Latest data（最新数据）** 里一眼就读得懂。

> ★ **关键**：预处理是在**服务端、存进历史之前**做的。
> 也就是说，之后所有地方 —— Latest data、触发器里的 `last()` —— **看到的都是这个"秒数"**，不再是时间戳。
> **这条就是下面阈值最容易算错的根源。**

### 6.3 建触发器

**Triggers（触发器）→ Create trigger（创建触发器）**

| 字段                 | 填什么                                                                        |
| -------------------- | ----------------------------------------------------------------------------- |
| Name（名称）         | `备份超过 26 小时没有成功`                                                    |
| Severity（严重性）   | **High（严重）**                                                              |
| Expression（表达式） | `last(/myblog-server/vfs.file.time[/opt/myblog/status/last_success]) > 93600` |

**为什么是 26 小时而不是 24**：备份每天 03:17 跑一次，正常间隔就是 24 小时。留 2 小时余量，避免「稍微晚一点就误报」—— 但又不至于宽到「漏掉一整天还不报」。

#### ★ `93600` 是怎么来的（这个数最容易填错）

```
26 小时 × 60 分 × 60 秒 = 93600 秒
```

⚠️ **千万别填成 `7200`。** `7200` 秒只有 **2 小时** —— 备份每天 03:17 跑完，到 05:17 就是「已经 2 小时没备份了」，于是：

- **每天固定误报一次**（05:17 左右）
- 而且会一直挂在 problem 状态，**到第二天 03:17 备份跑完才恢复**
- 一天里有 22 小时在报 —— 真正出事的那次反而淹没在噪音里

⚠️ 另外，因为上一步加了预处理，这里**不能**再写成 `now() - last(...) > 26h` 那种「两个时间戳相减」的写法：`last()` 拿到的已经是「多少秒前」，再拿 `now()` 去减它没有任何意义。

> **预处理和表达式是一对，改一个就得回头看另一个。**

**告警走哪条路**：直接复用你已经**实测通过**的 Zabbix 邮件链路（WSL2 → 163 SMTP，2026-10-09 停 nginx 演练验证过）。**不需要配任何新的 SMTP。**

### 6.4 验证它真的会响

```bash
# 把心跳文件的时间戳改成两天前
touch -d '2 days ago' /opt/myblog/status/last_success
```

等 5~10 分钟，**应该收到「备份超过 26 小时没有成功」的告警邮件**。

收完别忘了跑一次真备份把它恢复正常：

```bash
systemctl start myblog-backup.service
```

> ⚠️ **这是唯一能证明监控有效的方法。** 触发器配好了不等于会响 ——
> 和 Zabbix 那套一样的老话：**点测试不算，得真造一个故障出来。**

**实测记录（2026-10-11）**：照上面这套走完，**告警邮件收到了；跑完备份之后恢复邮件也收到了**。
也就是「会响」和「会停」两条路都验过 —— 不是只验了响、没验停。这一点值得说，因为**恢复邮件收不到等于告警永远挂在那，久了就没人看了**。

**已知代价**（这份方案里如实记着）：Zabbix Server 跑在笔记本的 WSL2 里，**笔记本关机 = 这套告警也停**。
所以它是"有人看着的时候管用"。要 24×7 的告警，得把 Zabbix Server 挪到云上 —— 那是另一件事，不在本轮。

## 7. 日常运维

```bash
# 今天备份成功了吗？
systemctl status myblog-backup.service
journalctl -u myblog-backup -n 20 --no-pager

# 下次什么时候跑？
systemctl list-timers myblog-backup.timer

# 两份副本都在吗？
ls -lh /opt/myblog/backup/*.sql.gz
ossutil -c /opt/myblog/backup/ossutil.conf ls oss://<备份桶>/daily/

# 心跳文件多老了？
ls -l /opt/myblog/status/last_success

# 磁盘还够吗（这台机器只有 40G）
df -h /opt
```

**要改保留期**：

| 改什么     | 改哪里                                                             |
| ---------- | ------------------------------------------------------------------ |
| 本地留几天 | [deploy/backup.sh](backup.sh) 里的 `KEEP_DAYS`（要 push 才会生效） |
| OSS 留几天 | OSS 控制台的生命周期规则（立刻生效，不用 push）                    |

**要升 ossutil 版本**：改 `group_vars/all/main.yml` 里的 `ossutil_version`，重跑 Ansible。
（装成带版本号的文件名 + 软链，所以旧版本还在，回退就是把软链指回去。）

## 8. ★ 灾难恢复：服务器整个没了怎么办

> 这是「备份」这个词的另一半。**没有这一节，前面做的都只是"存了文件"。**

**目标：从零到博客能访问，约 15 分钟。RPO ≈ 24 小时。**

```
① 准备一台新服务器（同地域、同配置）
      └─ 装上 Docker，确认能 SSH

② 拉代码 + 跑 Ansible
      cd ~/ansible && ansible-playbook site.yml --ask-vault-pass
      └─ 建目录、写 .env、装 ossutil、起备份定时器
      ⚠️ 此时网站还打不开 —— 数据库是空的

③ 从 OSS 把最新备份拉回来，导进生产库
      ossutil -c /opt/myblog/backup/ossutil.conf \
        cp oss://<备份桶>/daily/<最新那份> /tmp/restore.sql.gz
      gzip -dc /tmp/restore.sql.gz | docker exec -i myblog-mysql \
        sh -c 'exec mysql -uroot -p"$MYSQL_ROOT_PASSWORD" myblog'
      ⚠️ 注意这里是【导进生产库 myblog】—— 灾难恢复场景就是要覆盖它，
         和平时演练（导进临时库）不一样

④ push 一次，让 CI 把应用部署上去
      └─ 或者用 workflow_dispatch 手动触发

⑤ 验证
      curl http://127.0.0.1:8081/api/config/all
      └─ 再用浏览器打开页面，看一眼文章和图片都在
```

**恢复过程中最该记住的一句话**：第 ③ 步能成立，靠的是**备份文件里没有写死库名**（`mysqldump` 时故意没加 `--databases`）。这就是为什么不能图省事加那个参数。

**恢复完还要做的事**：

- 重新配 Zabbix Agent（`/opt/zabbix-agent/` 不在 Ansible 里，是手工装的）—— 见 [Zabbix监控方案.md](Zabbix监控方案.md) §6
- 确认安全组、`/opt/myblog/.env` 都在
- **手工跑一次备份 + 一次恢复演练**，确认新机器上的备份链路也是通的

## 9. 排错对照表

| 现象                                                       | 大概是什么                                                                                                        | 怎么查                                                                                                                            |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `event=backup_fail reason=dump_failed`                     | MySQL 容器没起来 / 密码不对                                                                                       | `docker ps \| grep myblog-mysql`；`docker compose logs mysql`                                                                     |
| `reason=no_ossutil_conf`                                   | Ansible 没跑过，或播放失败                                                                                        | `ls -l /opt/myblog/backup/ossutil.conf`                                                                                           |
| `reason=low_disk`                                          | 磁盘快满了                                                                                                        | `df -h /opt`；`docker system df`                                                                                                  |
| `reason=oss_upload_failed`                                 | 桶名错 / 凭据错 / 策略没加                                                                                        | `ossutil -c <配置> ls oss://<桶>/` 手工试一次，看具体报错                                                                         |
| ossutil 报 `too many arguments` / `unknown flag`           | `-c` 的位置不对                                                                                                   | 两个脚本里都用 `ossutil -c <配置> <子命令> …` 这个顺序（全局选项放最前面）；改 [backup.sh](backup.sh) 里那个 `oss()` 包装函数即可 |
| 报 `AccessDenied`，但只是上传                              | 策略里少了 `/*` 那条 Resource                                                                                     | 回 2.3 检查                                                                                                                       |
| `reason=no_table_in_dump`                                  | 库名错了，导出的是个空库                                                                                          | 看 `.env` 里的 `MYSQL_DATABASE`                                                                                                   |
| 定时器到点了没跑                                           | 上一次还没结束 / timer 没启用                                                                                     | `systemctl list-timers`；`systemctl status myblog-backup`                                                                         |
| 日志里只有 `backup_start` 没有后续                         | 脚本卡住了                                                                                                        | `TimeoutStartSec=1800` 兜底；查 MySQL 是不是半死不活                                                                              |
| 心跳告警一直响                                             | 备份确实没成功                                                                                                    | 先看 `journalctl -u myblog-backup`                                                                                                |
| 心跳告警**每天同一个点**响一次，过一阵又自己恢复，天天如此 | 触发器阈值填成了 `7200`（2 小时），本该是 `93600`（26 小时）—— 加了预处理之后 `last()` 拿到的是「秒数」不是时间戳 | 回 6.3 把表达式改成 `> 93600`                                                                                                     |
| Agent 报 `Permission denied`，监控项变 **unsupported**     | 心跳文件所在的**目录**太紧（0700），容器里是非 root（uid 1997），穿不过去                                         | `ls -ld /opt/myblog/status` 应是 `0755`。★ **卡住的是目录不是文件**；`docker exec -u root …` 能读就证明是权限问题、跟挂载无关     |
| 演练报 `Unknown database 'myblog'`                         | 备份时误加了 `--databases`                                                                                        | 检查 `backup.sh` 里 mysqldump 的参数                                                                                              |

## 10. 这套东西里最值得说的四个点

如果面试被问「你备份是怎么做的」，按这个顺序讲：

1. **双副本 + 各自防什么**
   本地那份防手滑，OSS 那份防机器没了。**不吹它是完美的 3-2-1** —— 本地和源数据在同一块盘上，这个短板我清楚。

2. **备份账号没有删除权限，清理交给生命周期规则**
   脚本删不掉备份，服务端按规则删。**凭据泄漏也清不掉历史备份。**
   验证方式是拿它去删一个文件，看它报不报错。

3. **监控的是「备份有没有按时发生」，不是「脚本有没有报错」**
   脚本没跑的时候是没有错误可抓的，只有时间戳能暴露。用 `vfs.file.time` 取心跳文件的 mtime，
   在服务端预处理成「多少秒前」，触发器卡 26 小时（`93600` 秒 = 间隔 24 + 2 小时余量）。
   **告警和恢复都真造过故障验过。**

4. **做过恢复演练，而且演练是从 OSS 拉的**
   `set -euo pipefail`、`--single-transaction`、gzip 校验、逐表对数 ——
   这些都是为了确保「拿到的不是一份看起来成功的假备份」。
   **只备份不验证恢复，等于没有备份。**

**如果能再加一句**：这次备份体系的起因是 2026-10-10 那次数据误删 —— 那件事让我意识到，**光有"备份动作"是不够的，得能证明它真的能恢复**。
