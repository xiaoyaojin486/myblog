## 0. 总览：Ansible 和 GitHub Actions 分别干什么

### 0.1 一句话概括

**v1 的问题**：博客的数据库**借住在另一个项目的 `myapp-mysql` 容器里**，还借用了它的 Docker 网络。于是 `deploy/` 下几乎**每个文件都带着 `myapp` 的痕迹**——换一台机器、换一个环境，整套东西就废了。

**v2 做的事**：把 MySQL 变成**博客自己的一个容器**（`myblog-mysql`）。从此 `deploy/` 下**再也不出现 `myapp` 三个字**。

> **可复用性的验收标准**：把这套 `deploy/` + `~/ansible` 原样拿到另一台机器上，只改 `.env` 里的域名/IP，就能跑起来 —— **不需要知道那台机器上还有别的什么项目**。

### 0.2 从头到尾，就这么几步

```
你（本地 WSL）
  │  ① 手动跑一次：ansible-playbook site.yml
  ▼
服务器 /opt/myblog/
  │     布置好了：目录 + .env + sql/init.sql
  │     （注意：还没有 docker-compose.yml，这是正常的）
  │
  │  ② git push
  ▼
GitHub Actions（在 GitHub 的机器上跑）
  │     编译 jar 和 dist
  │     把 jar / dist / docker-compose.yml / Dockerfile / nginx 配置 scp 到服务器
  │     SSH 进服务器执行 docker compose up -d
  ▼
博客跑起来了 —— 浏览器打开 http://服务器IP:8081
```

**这套东西只有两半，各管各的：**

| | **Ansible** | **GitHub Actions** |
|---|---|---|
| 一句话 | 把服务器**布置好** | 把代码**送上去跑起来** |
| 它在哪台机器上跑 | 你的 WSL，通过 SSH 连服务器 | GitHub 的机器，通过 SSH 连服务器 |
| 什么时候跑 | **手动敲**，一台新服务器跑一次 | **每次 push 到 main，自动跑** |
| 管的是 | **环境**：目录、密钥、脚本、镜像 | **版本**：代码、构建产物、启动 |
| 碰代码吗 | ❌ 完全不碰 | ✅ 它存在的意义就是送代码 |
| 跑完的状态 | 目录铺好了，但**服务一个都没起** | 服务跑起来了，**能访问了** |
| 失败了会怎样 | 报错停下，你改完重跑 | Actions 页面变红，日志里有原因；要退回旧版本得手动跑 `rollback.sh` |
| 改了它要重跑吗 | 改了初始化配置 → 重跑 | 不需要，push 就自动跑 |

> **为什么非要分成两半？** 因为「搭环境」和「发版本」的节奏完全不同。
> 环境一年搭一次，版本一天可能发十次。硬塞进一个流程里，要么每次都白搭一遍环境，要么环境永远搭不齐。

### 0.3 Ansible 干的 5 件事（跑一次）

`site.yml` 从头到尾就这些，按顺序执行：

| # | 干什么 | 具体动作 | 为什么 |
|---|---|---|---|
| 1 | **体检** | 查 Docker 装没装；查 8081 端口被哪个容器占着 | 被**别的**容器占着就立刻停下报错，不往下走（被自己的 `myblog-nginx` 占着是正常的） |
| 2 | **调 Docker** | 写 `/etc/docker/daemon.json`：配国内镜像加速器 + 日志轮转，然后重启 Docker | 不配加速器，拉镜像能卡到天荒地老 |
| 3 | **预拉镜像** | `docker pull` 四个基础镜像：`eclipse-temurin:21-jre`、`nginx:alpine`、`redis:7-alpine`、`mysql:8.0` | 提前拉好，等 CI/CD 部署时就不用现场拉了。首次慢，之后命中缓存 |
| 4 | **建目录** | 建 `/opt/myblog/` 底下的 8 个目录 | 后面所有东西都往这里放 |
| 5 | **放两个文件** | 传 `sql/init.sql`；用 Vault 里的密钥渲染出 `.env` | 这两个必须在**容器启动之前**就位 |

**跑完之后，服务器上长这样：**

```
/opt/myblog/
├── .env                 ← ✅ 有了（权限 0600，只有属主能读，因为里面全是明文密码）
├── sql/init.sql         ← ✅ 有了
├── backend/             ← 空目录
├── frontend/            ← 空目录
├── nginx/               ← 空目录
├── logs/                ← 空目录
├── redis-data/          ← 空目录
├── mysql-data/          ← 空目录（MySQL 第一次启动后，这里会热闹起来）
└── docker-compose.yml   ← ❌ 没有！！这是正常的
```

> **⚠️ 最常见的误会**：ansible 跑完发现没有 `docker-compose.yml`，以为出错了。
> **没出错。** 这个文件由 GitHub Actions 每次部署时送过来，而且会在 `docker compose up -d` **之前**就位。你在服务器上手敲 `docker compose` 命令会失败，是因为**还没 push 过**——push 一次就有了。

### 0.4 GitHub Actions 干的 5 件事（每次 push）

`deploy.yml` 里有 **3 个 job**：

```
push 到 main
   │
   ├──→ job 1  build-backend    在 GitHub 的机器上：
   │            checkout → 装 JDK 21 → mvn package → 得到 app.jar
   │
   └──→ job 2  build-frontend   在 GitHub 的机器上：
                checkout → 装 Node 20 → npm ci → npm run build → 得到 dist/
                │
                │  两个都成功了才继续
                ▼
        job 3   deploy
                │
                ├─ ① 组装发布目录
                │      jar 改名成 app.jar（Maven 出来叫 bootstrap-1.0.0.jar，Dockerfile 里写的是 app.jar）
                │      带上 docker-compose.yml / backend/Dockerfile / nginx/default.conf / rollback.sh
                │
                ├─ ② scp 到服务器 /opt/myblog/_incoming
                │
                ├─ ③ SSH 进服务器执行：
                │      a. 守卫：.env 和 sql/init.sql 在不在？不在就报错退出
                │      b. 备份当前版本（app.jar.prev / dist.prev）← 回滚要用
                │      c. 把 _incoming 里的文件搬到正式位置
                │      d. docker compose build backend
                │      e. docker compose up -d      ← ★★★ MySQL 在这里第一次启动
                │      f. docker compose restart nginx   （让 nginx 重新解析 backend 的 IP）
                │      g. 冒烟测试：curl 本地 8081，最多等 180 秒
                │
                └─ ④ 通过 → docker image prune -f 清理悬空镜像
                   失败 → 打印 backend 和 mysql 各 50 行日志，退出码 1
```

**这 5 件事理一遍：**

| # | 干什么 | 在哪台机器上 |
|---|---|---|
| 1 | 编译后端（Maven → jar） | GitHub |
| 2 | 编译前端（npm → dist） | GitHub |
| 3 | 把构建产物**和 4 个配置文件**一起 scp 到服务器 | GitHub → 服务器 |
| 4 | SSH 进服务器，切版本 + `docker compose up -d` + 重启 nginx | 服务器 |
| 5 | 冒烟测试；通过就清理，失败就报出日志 | 服务器 |

> **为什么要重新编译？** 因为是 CI/CD —— 它存在的意义就是「你只管 push，剩下的它来」。
> 服务器上没有 Maven 也没有 Node，所以构建必须在 GitHub 的机器上做完，只把**结果**（jar、dist）送过去。

### 0.5 边界：谁碰什么、谁不碰什么

这一栏最容易搞混，单独列一张表：

| 东西 | 谁把它放上去 | 谁不碰 |
|---|---|---|
| `.env`（全部密钥） | **Ansible**（从 Vault 渲染） | Actions 只读不写 |
| `sql/init.sql` | **Ansible** | Actions 只检查在不在 |
| `docker-compose.yml` | **Actions**（每次覆盖） | Ansible 不传 |
| `backend/Dockerfile` | **Actions** | Ansible 不传 |
| `nginx/default.conf` | **Actions** | Ansible 不传 |
| `rollback.sh` | **Actions** | Ansible 不传 |
| `backend/app.jar` | **Actions**（GitHub 上现编译） | Ansible 不传 |
| `frontend/dist/` | **Actions** | Ansible 不传 |
| 数据库 `myblog` | **MySQL 容器自己**（首次启动时） | Ansible 和 Actions **都不建** |
| 数据库账号 `myblog` | **MySQL 容器自己**（读 `.env` 里的变量） | 同上 |
| 表和初始数据 | **MySQL 容器自己**（执行 `init.sql`） | 同上 |

**三句话记住：**

1. **Ansible 管「密钥和脚本」** —— 这些东西 Actions 拿不到，因为密钥在 Vault 里，CI 里没有。
2. **Actions 管「代码和启动」** —— 这些东西每次都在变。
3. **数据库谁都不管** —— 容器第一次启动时自己搞定（建库、建账号、建表、灌数据，一口气做完）。

> 第 3 条是本方案和 v1 最大的不同。v1 里这三件事是 Ansible 钻进 `myapp-mysql` 容器里手敲 SQL 做的；
> 现在容器是自己的了，它启动时自己就做完了 —— 具体是哪几个环境变量驱动的，见 **3.5 节**那张「删掉的任务 / 现在谁做」对照表。

### 0.6 完整时间线（从一台新服务器到博客能访问）

| # | 谁在做 | 做什么 | 做完之后 |
|---|---|---|---|
| 1 | **你** | 停掉 `myapp-backend` | 今晚 2 点那个删文件的定时任务不会再跑 |
| 2 | **你** | `ansible-playbook site.yml` | `/opt/myblog/` 铺好了（还没有 compose 文件） |
| 3 | **你** | `git push` | GitHub Actions 被触发 |
| 4 | **Actions** | 编译 jar + dist | 构建产物好了 |
| 5 | **Actions** | scp + `docker compose up -d` | **MySQL 首次启动 → 建库、建账号、建表、灌数据** |
| 6 | **Actions** | 冒烟测试 | 通过 = 这次部署成功 |
| 7 | **你** | 浏览器打开 `http://服务器IP:8081` | 博客活了 |

**第 5 步是整条链上最容易出问题的一环**，因为它把「建库建账号建表」和「起服务」压在了同一次动作里。真出问题，去看 `docker compose logs mysql`。

## 1. 改了什么（对照表）

一共 14 处耦合，全部指向 `myapp-mysql` / `myapp_app-network`：

| # | 位置 | 原来（v1） | 现在（v2） |
|---|---|---|---|
| 1 | `docker-compose.yml` → `backend.networks` | `myblog` + `myapp_net` | **只有 `myblog`** |
| 2 | `docker-compose.yml` → `networks:` 段 | 多一个 `myapp_net: external: true` | **删掉** |
| 3 | `docker-compose.yml` → 服务列表 | 没有 mysql | **★ 新增 `mysql` 服务** |
| 4 | `group_vars/all/main.yml` | `myapp_network` + `mydb_container: myapp-mysql` | **只留 `mydb_container: myblog-mysql`** |
| 5 | `group_vars/all/main.yml` → `base_images` | 只有 temurin + nginx | **补上 `redis:7-alpine`、`mysql:8.0`** |
| 6 | `vault.yml` | 不需要 MySQL root 密码 | **★ 新增 `vault_mysql_root_password`** |
| 7 | `env.j2` | `MYSQL_HOST={{ mydb_container }}`（= myapp-mysql） | `MYSQL_HOST=myblog-mysql`，**加 root 密码一行** |
| 8 | `site.yml` → 前置检查 | 查 myapp 网络、查 myapp-mysql 容器、查 tlias 库 | **全删**，换成「8081 端口占用检查」 |
| 9 | `myblog-init/tasks/main.yml` | 5 个 `docker exec myapp-mysql …` 任务 | **★ 全删**，只剩「建目录 + 传 SQL + 渲染 .env」 |
| 10 | 建库 / 建账号 / 建表 | Ansible 钻进**别人的**容器执行 SQL | **MySQL 容器首次启动自己完成** |
| 11 | `.github/workflows/deploy.yml` | `docker compose up -d backend redis nginx`（注释写着「不含 mysql——那是另一个项目的」） | **`docker compose up -d`**（全量） |
| 12 | 验收清单第 7 项 | 访问另一个项目，确认没搞坏 | 换成「确认 4 个 `myblog-*` 容器齐全、且找不到 `myapp-*`」 |
| 13 | 附录诊断命令 | `docker network inspect myapp_app-network` … | 换成本地网络的命令 |
| 14 | §1.4 隔离边界 / §2.3 内存预算 | 整节围绕「共用」写 | **作废**，由本文第 2 节取代 |

**不用改的**：`deploy/backend/Dockerfile`、`deploy/nginx/default.conf`、`deploy/rollback.sh`、`deploy/ansible/inventory.ini`、`deploy/ansible/roles/docker/**`、`~/ansible/ansible.cfg`。

### ⚠️ 1.1 v2 **没有**解决的那一处耦合：OSS 桶

v2 拆的是**数据库**。但博客和另一个项目还**共用着同一个 OSS 桶 `hu-tlias`** —— 这就是 2026-10-10 图片被删那件事的根源。

**这次是靠「另一个项目整个搬走」顺带解决的，不是靠方案本身解决的。** 所以：

- **短期**：`myapp` 删除之后，桶里只剩博客在用了，问题暂时消失
- **长期**：**给博客单独开一个桶**（比如 `hu-myblog`），是唯一彻底的办法

> **为什么值得现在就记一笔**：这套 `deploy/` 的设计目标是「搬到任何一台机器都能跑」。而桶是**跨项目共享的资源**——只要将来还有第二个程序用同一个桶，那个程序的「清理垃圾」逻辑就会再删你一次。
>
> **顺带两条纪律**（和本次事故直接相关）：
> 1. **每个桶都开版本控制** —— 10 月 9 日那次没开，文件是真没了；10 月 10 日开了，一条「恢复」就回来了
> 2. **一个程序一把 AccessKey，每把钥匙的 RAM 策略只允许动自己的前缀** —— 这次两边共用一把钥匙，从日志上根本看不出是谁干的

## 2. 新架构与内存

### 2.1 架构图（v2）

```
┌─────────────────── 阿里云 ECS ───────────────────┐
│  公网 :8081                                       │
│   └─ myblog-nginx ──┬── /       → 博客前端静态文件 │
│                     └── /api/   → myblog-backend  │
│                                                   │
│   ┌────────── myblog_net（博客自己的网络）──────┐ │
│   │  myblog-nginx                             │ │
│   │  myblog-backend（java -jar app.jar）      │ │
│   │  myblog-redis                             │ │
│   │  myblog-mysql   ★ v2 新增，博客自己的库    │ │
│   └───────────────────────────────────────────┘ │
│                                                   │
│   （服务器上还有没有别的项目，与本方案无关）      │
└───────────────────────────────────────────────────┘
```

**四个容器全在 `myblog_net` 里**，靠 Docker 内置 DNS 按名字互相解析。整个方案**不引用任何外部网络、外部容器**。

### 2.2 内存：这次为什么放得下了

v1 之所以共用 MySQL，**只有一个原因：内存不够**。当时算的账是：

| | 方案 A：共用（v1 选的） | 方案 B：自建（v1 否掉的） |
|---|---|---|
| MySQL | 0（复用 `myapp-mysql`） | ~200 MiB |
| **合计** | **~300 MiB** | **~500 MiB** |
| 剩余（可用 638 MiB） | ~340 MiB ✅ | **~140 MiB ⚠️ 太危险** |

**v2 为什么就放得下了** —— 因为另一个项目要走了，它占的内存会**整个腾出来**：

| 来源 | 释放 |
|---|---|
| `myapp-backend`（`java -jar app.jar`，没设 `-Xmx`，默认吃 1/4 物理内存） | ~304 MiB |
| `myapp-mysql` | ~384 MiB |
| `myapp-frontend` | ~4 MiB |
| **合计腾出** | **~692 MiB** |

所以新的账是：

| | v2 |
|---|---|
| 可用内存 | 638 + 692 ≈ **1330 MiB** |
| `myblog-mysql`（调优后） | ~250 MiB |
| `myblog-backend` | ~280 MiB |
| `myblog-redis` | ~15 MiB |
| `myblog-nginx` | ~5 MiB |
| **合计占用** | **~550 MiB** |
| **剩余** | **~780 MiB** ✅ |

> **⚠️ 过渡期注意**：在另一个项目**删掉之前**，两个 MySQL 会同时在跑。所以执行顺序里**第一步就是停掉 `myapp-backend`**（见第 5 节）——它一停，内存就够了。

### 2.3 三个 MySQL 参数为什么必须加

`mysql:8.0` 默认是按「服务器 4G 起步」调的，直接搬过来会撑爆这台机器：

| 参数 | 作用 |
|---|---|
| `--innodb-buffer-pool-size=128m` | 默认也是 128M，但**写死**才不会被 MySQL 自己按物理内存调大 |
| **`--performance-schema=OFF`** | **最值钱的一条，省 ~100 MiB**。性能监控表在小机器上是纯负担 |
| `--max-connections=50` | 默认 151，**每个连接都要分内存**。博客是单管理员，50 够得不能再够 |

另外 `mem_limit: 384m` 兜底。如果 mysql 被系统杀掉，看：

```bash
docker inspect myblog-mysql -f '{{.State.OOMKilled}}'
```

输出 `true` 就是被内存限制挤死了，把 `mem_limit` 调到 `512m`。

## 3. 要改的文件（完整内容）

> 这一节的文件，等你看完点过头，我会**照着这份内容把 `deploy/` 下的文件重写一遍**。

### 3.1 `deploy/docker-compose.yml`

```yaml
services:
  # ===== ★ v2 新增：博客自己的数据库，不再借 myapp-mysql =====
  mysql:
    image: mysql:8.0          # 服务器本地已有，Ansible 会预拉
    container_name: myblog-mysql
    restart: unless-stopped
    env_file: [.env]          # 复用同一份 .env，少维护一个文件
    # 三个 ★ 参数：这台机器只有 2G，默认配置撑不住（见新版部署方案 2.3）
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_general_ci
      - --innodb-buffer-pool-size=128m
      - --performance-schema=OFF
      - --max-connections=50
    volumes:
      - ./mysql-data:/var/lib/mysql
      # ★ 关键：这个目录里的 .sql 只在「数据目录为空」时执行一次。
      #   所以建表这件事从 Ansible 手里搬到了这里 —— 首次启动自动完成。
      - ./sql/init.sql:/docker-entrypoint-initdb.d/01-init.sql:ro
    mem_limit: 384m
    healthcheck:
      # 真的连上去查一次，确保「服务起来了」且「密码已经生效」
      test: ["CMD-SHELL", "mysql -h127.0.0.1 -uroot -p\"$$MYSQL_ROOT_PASSWORD\" -e 'SELECT 1' >/dev/null 2>&1"]
      interval: 5s
      timeout: 5s
      retries: 30
      start_period: 60s       # MySQL 首次初始化要 30~60 秒，别急着判它失败
    networks: [myblog]

  backend:
    build: ./backend
    image: myblog-backend:latest
    container_name: myblog-backend
    restart: unless-stopped
    env_file: [.env]
    mem_limit: 512m
    volumes:
      - ./logs:/app/logs
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
    networks: [myblog]        # ★ v2：只剩自己的网络，不再 join myapp_app-network

  redis:
    image: redis:7-alpine
    container_name: myblog-redis
    restart: unless-stopped
    environment:
      REDIS_PASSWORD: ${REDIS_PASSWORD}
    command: >
      sh -c 'redis-server --requirepass "$$REDIS_PASSWORD"
             --appendonly yes --maxmemory 80mb --maxmemory-policy allkeys-lru'
    healthcheck:
      test: ["CMD-SHELL", "REDISCLI_AUTH=$$REDIS_PASSWORD redis-cli ping | grep -q PONG"]
      interval: 5s
      timeout: 3s
      retries: 10
    mem_limit: 96m
    volumes:
      - ./redis-data:/data
    networks: [myblog]

  nginx:
    image: nginx:alpine
    container_name: myblog-nginx
    restart: unless-stopped
    ports:
      - "8081:80"
    volumes:
      - ./frontend/dist:/usr/share/nginx/html:ro
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [backend]
    mem_limit: 64m
    networks: [myblog]

networks:
  myblog:
    name: myblog_net
# ★ v2：myapp_net 整段删掉了 —— 博客不再需要任何外部网络
```

#### 两个设计点

**① `env_file: [.env]` 给 mysql 用，会不会把数据库密码泄给后端？**

后端和 mysql **共用同一份 `.env`**，所以后端容器的环境变量里**确实会看到 `MYSQL_ROOT_PASSWORD`**。这是 v2 为了「少一个文件、少一处漏配」做的取舍。

> **想更严一点（可选，不影响本次走通）**：把 root 密码单独放 `/opt/myblog/mysql.env`，`mysql` 服务改成 `env_file: [mysql.env]`，`.env` 里就不放 root 密码了。**本次先不做**——两个文件容易漏配，等整套跑稳了再收紧。

**② 为什么 `init.sql` 挂在 `docker-entrypoint-initdb.d`**

这是 MySQL 官方镜像的约定目录：**数据目录为空时**（也就是第一次启动），它会把里面所有 `.sql` 按文件名顺序执行一遍。

v1 之所以要 Ansible 写 5 个任务去 `docker exec` 建库建账号建表，是因为**容器不是我们的**，只能钻进去手动补。现在容器是自己的，这三件事**它启动时自己就做完了**。

> 「自己拥有的资源」和「借来的资源」的差别就在这里 —— **借来的东西，你只能绕开它的自动化，用手动的方式去补。**

## 4. 老数据怎么搬过来

**这步是可选的，但强烈建议做** —— 不做的话，博客的文章、管理员账号、图片记录都会重来一遍（OSS 上的图片文件本身还在，但数据库里指向它们的记录没了）。

> **⚠️ 顺序**：必须在 **Ansible 跑完**（`.env` 和 `mysql-data` 目录就绪）之后、**第一次 `docker compose up -d` 之前**做。

### 第 1 步：从旧容器里导出

```bash
# 密码走容器自己的环境变量，不经过命令行 —— 不会留在 shell history 里
docker exec -i myapp-mysql sh -c \
  'mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" \
     --single-transaction --routines --triggers --default-character-set=utf8mb4 \
     myblog' > /opt/myblog/sql/myblog-backup-$(date +%F).sql
```

### 第 2 步：确认导出的文件里有东西（**别跳过**）

```bash
ls -lh /opt/myblog/sql/myblog-backup-*.sql
grep -c "INSERT INTO" /opt/myblog/sql/myblog-backup-*.sql
```

- 文件只有几百字节、`INSERT INTO` 数是 0 → **库是空的，没什么可搬，后面几步直接跳过**
- 有几十 KB 以上、`INSERT INTO` 有若干条 → 继续

### 第 3 步：起新的 mysql 容器（先只起它）

```bash
cd /opt/myblog
docker compose up -d mysql
docker compose logs -f mysql          # 看到 "ready for connections" 再按 Ctrl+C
```

### 第 4 步：导入

```bash
docker exec -i myblog-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" myblog' \
  < /opt/myblog/sql/myblog-backup-2026-10-10.sql
```

> **看到一堆 `DROP TABLE` 别慌** —— `mysqldump` 默认会带 `DROP TABLE IF EXISTS`，所以就算 `init.sql` 已经把表建好了，导入也会**先删再建**，不会冲突。
>
> **如果报 GTID 相关的错**，在导出命令里加一个 `--set-gtid-purged=OFF` 重来一次。

### 第 5 步：核对

```bash
docker exec -i myblog-mysql sh -c \
  'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -N -e "use myblog; show tables; select count(*) from sys_user;"'
```

和老库对一下行数，一致就搬完了。

## 7. v2 新增的坑

### ① `init.sql` 改了不生效

**现象**：往 `sql/init.sql` 里加了张表，重新部署后表没出现。
**原因**：`docker-entrypoint-initdb.d` **只在数据目录为空时执行**。`/opt/myblog/mysql-data` 已经有数据了，它就不看了。
**解决**：手工进容器执行那段 SQL，或者用迁移工具（Flyway/Liquibase）。**上生产库以后不要靠 `init.sql` 改结构。**

```bash
docker exec -i myblog-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" myblog' < 新的.sql
```

### ② 改了 `.env` 里的 `MYSQL_ROOT_PASSWORD` 没反应

**原因**：MySQL 的 root 密码**存在数据目录里**，环境变量只在**首次初始化**时被采用。数据目录已存在 → 环境变量形同虚设。
**解决**：进容器改：

```bash
docker exec -it myblog-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "ALTER USER \"root\"@\"%\" IDENTIFIED BY \"新密码\";"'
```

改完**记得同步改 `.env`**，否则下次 healthcheck 会一直失败。

### ③ `myblog-mysql` 反复重启 / 被 OOM Kill

**现象**：`docker ps` 里 mysql 状态是 `Restarting`，或日志里有 `Killed`。
**诊断**：

```bash
docker inspect myblog-mysql -f '{{.State.OOMKilled}}'    # true 就是内存不够
docker compose logs --tail=50 mysql
```

**解决**：把 compose 里 mysql 的 `mem_limit: 384m` 调到 `512m`（内存账算下来还有 ~780 MiB 余量，给得起）。

### ④ 首次部署冒烟测试超时

**现象**：第一次 `docker compose up -d`，冒烟测试等不到后端起来。
**原因**：MySQL 首次初始化要 30~60 秒，后端 `depends_on: service_healthy` 一直在等。总共可能要 2 分钟。
**解决**：workflow 里的等待循环已经放宽到 60 次（180 秒）。**如果还是超时**，去服务器上手动看：

```bash
docker compose ps
docker compose logs --tail=50 mysql
```

### ⑤ `MYSQL_HOST` 又填成了 `localhost`

**现象**：后端报连不上数据库。
**原因**：容器里的 `localhost` 指**容器自己**，不是别的容器。
**解决**：模板里已经写死成 `myblog-mysql`（容器名 = 主机名，靠 `myblog_net` 的 Docker DNS 解析）。**别手改。**

### ⑥ `project_root` 写成了相对路径

**现象**：Ansible 跑到「上传建表脚本」时报找不到文件。
**原因**：playbook 跑在 `~/ansible`，跟仓库没有相对关系。
**解决**：`group_vars/all/main.yml` 里必须写**绝对路径**（见 3.2）。v1 的仓库快照里残留着 `{{ playbook_dir }}/../..`，本次已修正。

## 8. 改完之后，`deploy/` 长什么样

```
deploy/
├── 部署方案.md                    ← v1，保留（环境准备、Secrets、回滚那几章仍然要看）
├── 新版部署方案.md                ← ★ 本文
├── docker-compose.yml             ← 改：+mysql 服务，-myapp_net
├── backend/Dockerfile             ← 不改
├── nginx/default.conf             ← 不改
├── rollback.sh                    ← 不改
└── ansible/
    ├── inventory.ini              ← 不改
    ├── site.yml                   ← 改：前置检查换掉
    ├── ansible.cfg                ← 不改（实际用的是 ~/.ansible.cfg）
    ├── group_vars/all/
    │   ├── main.yml               ← 改：-myapp_network，+mysql:8.0/redis:7-alpine，project_root 绝对路径
    │   └── vault.yml              ← ★ 你自己用 ansible-vault edit 加一行
    └── roles/
        ├── docker/**              ← 不改
        └── myblog-init/
            ├── tasks/main.yml     ← 改：5 个任务砍成 3 个
            └── templates/env.j2   ← 改：MYSQL_HOST + root 密码
```

**验收「可复用性」的一句话**：配置里不该再出现 `myapp` 了。

```bash
# 先把每行「# 之后」的内容剪掉（注释不算），再看还剩不剩 myapp
grep -rn myapp deploy/ --exclude='*.md' | sed 's/#.*//' | grep myapp
```

**这条命令应该没有任何输出。** 有输出就说明还有真在用的地方，得回头改。

为什么不直接 `grep -ril myapp deploy/`？因为改完的文件里**故意留着几处 `myapp` 注释**，
比如 `roles/myblog-init/tasks/main.yml` 开头那句「v1 里那 4 个 `docker exec myapp-mysql ...`
的任务全部删掉了」—— 那是给以后翻文件的你解释「为什么少了 4 个任务」的，删掉反而看不懂了。
上面那条命令把注释剪掉再比，比的就是「真正会执行的配置值」。
